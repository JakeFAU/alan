# Structural correction: source design scrutiny

Read-only investigation, 2026-11-13. No production edits or tests performed by this reviewer. The interrupted batching prototype is not evidence of a correct optimization. Runner references below were checked in the committed source, initially `2484251` and then merged baseline `ef38ca47179d86e7544885471ae43e86e1d6351e`; other line references identify the merged baseline. The controller owns qualification and delivery.

## Recommendation and boundary

Amend the original call-local-only contract prospectively, preserving its original text and measurements. Permit a disposable, single-Store affected-work index that survives ordinary `Run` calls. It must contain candidate identities and dependency indexes, never permission, dispatch authority, or accepted outcomes used to bypass the original transaction checks. Initialize it only after independent Create/Open validation and Open's epoch activation. Preserve independent Replay and inspection.

This can remove repeated visits to unrelated waiting/completed roots, runs, observations, and settled intents for the bounded series. It is not a small SQL rewrite, and it does not establish generally linear execution: affected scopes can have large dependency sets, live delivery frontiers can be large, ordinary final gates still reconstruct evidence, and full report output remains quadratic over B calls with B roots. The smallest defensible implementation is staged; root/report indexing and run-local observation indexing are useful independently, while complete negative readiness/delivery reuse requires an audited mutation seam.

Do not ship a hook-only invalidation scheme. Prefer explicit committed deltas and conservative fallback on unrecognized mutations. A limited update hook may supplement diagnostics; it cannot establish completeness.

### Preferred first implementation: guarded static composition

The controller's narrower proposal is the preferred implementation boundary. Optimize only independently validated static composition with no invocation templates, handoff/dynamic binding, reconciliation, or request-authority profile; keep existing traversal for other shapes. Determine eligibility from the validated complete provision/profile and programs, not merely the current absence of dynamic rows. `author/series.go:46-53,127-137,215-216` supplies direct evidence that the target workload has static generation-one runs, no invocation templates, one member/effect per root, retained dispatch admissions, and protected continuation slots. Do not key the optimization on application names or benchmark IDs.

Whitelist committed deltas only for the actual hot paths listed below. Unknown or unsupported intent kinds/operations cause baseline fallback before specialized discovery can drop them. A generic successful mutation invalidates the entire fast path for that owner lifetime; every direct commit must either record its exact permitted delta or invalidate. Rollbacks do not publish deltas. This is much smaller than implementing the full invalidator table below, which remains the checklist for fallback coverage and any future expansion.

Concrete initial eligibility can deliberately be narrower than all static composition: validated invocation-protocol profile with no templates, request authority, reconciliation, or handoff programs; each configured root owns exactly its generation-one root run; all retained runs/memberships agree with those static roots; no dynamic members/invocations/bindings, retry/lifecycle changes, composition closures, non-adapter intents, or nonempty terminal destination lists; only ordinary adapter outcomes are retained. Limits and profile are immutable for the owner; no main/temp triggers are installed. Continuation slots and ordinary adapter dispatch-admission recording are allowed. On reopening a historical store that fails any of these conditions, use baseline. These checks combine validated profile/program shape with retained state; checking table emptiness alone is insufficient. This deliberately excludes more cases than necessary to make the first proof small, without changing their behavior through the baseline path. Runtime code should test semantic shape, never author package names or exact program hashes.

All other successful mutating commits use generic invalidation. Read-only/no-write paths can preserve the index only when their pre-transaction guard succeeded and no unexpected counter/schema/context change occurred. Error-after-commit boundaries must not lose their deltas. The remaining all-protocol invalidator inventory below specifies reasons to fall back, not additional first-patch implementation work.

Keep separate baseline helpers. Initialize all static run/root identities once, lazily evaluate readiness at the normal traversal point, and retain negative certificates only within this guarded shape. Root preparation remains the existing function; each affected root in this workload has one member and one effect, so its dependency walk has an explicit constant bound. Receipt conflict, lifecycle/retry/adoption, newly admitted membership, general invocation, request authority, reconciliation, and arbitrary direct writes may conservatively disable the fast path instead of receiving new incremental semantics. The newly merged request-binding functionality remains supported through baseline execution; no speedup is claimed for it.

Full default reports can use one grouped intent/membership/charge pass and unchanged per-record validators, costing O(N + required output) per Run, without persistent cached report objects. That removes the root-by-intent product while leaving the explicit output/history scan bound. This limited design qualifies as a structural correction to the measured bounded workload if counters prove the per-turn global walks disappear, the whitelist has complete commit coverage, and full-mode evidence is unchanged. It does not qualify as a universal executor complexity claim.

Compact report mode is a separate gated step after the first structural patch is measured, not first-patch scope. If later authorized, it must be a documented existing-RunOptions mode, with full output as the zero/default value and omitted detail unambiguously distinguished from an empty result. Preserve all diagnostic/error behavior: guarded mode can validate changed evidence, and fallback mode can build/validate the ordinary report before omitting fields. Do not promise compact speedups in fallback mode. Keep the baseline timing comparison in full mode; compact-mode timing is a separate caller-choice comparison.

## What the source actually repeats

* `runner.go:131,245,264`: every scheduling turn asks for all pending deliveries, readiness, and all-root settlement. `last` and `attempted` are correctly local to one Run (`113-114`). Changing their lifetime would change behavior.
* `runner.go:320-404`: `selectReady` reads every run ID and every observation, sorts all observation IDs, visits runs in rotation, then filters the global observations for each receiving run. This is independent of whether only one run changed. `replay.go:296-327` validates consumed observations too; restricting validation to unconsumed observations silently weakens the contract.
* `runner.go:425-519`: pending delivery builds from all retained intents and terminal obligations, probes per operation, and sorts by delivery key. Invocation readiness is not just absence of delivery: `prepareInvocation` handles retained admission, publication, refusal and scope preparation (`invocation_outcome.go:291-321`).
* `composition_root.go:87-108`: all configured roots are prepared each turn; even finished roots remain in the loop. Root list order comes from the profile, not necessarily report order.
* `composition_inspect.go:31-123`: full reporting reads all intents, then loops over every intent for each root. Membership SQL is already reused per source run, but the Go root-by-intent product remains. Charges use a per-root filtered sum without a root-leading schema index (`58`; schema in `composition_store.go:25`). Merely adding an in-memory root candidate list does not remove those SQLite scans.
* `runner.go:521-620`: final reporting walks all roots, runs, intents and pending deliveries. Required output and re-derivation are different costs. Full report materialization is unavoidable for the existing contract; repeated root-by-intent matching and settled-intent probing are avoidable.

## Minimum state and lifetime

Keep one private state under `s.mu`, associated with the pinned `s.conn`, namespace, limits, schema/profile context and owner lifetime (`store.go:76-98,184-210`). No package-global maps, serialized cache, background scheduler, new table/index, or new dependency.

The state needs these identity indexes, populated once and updated only for affected records:

1. Ordered RunIDs; a candidate set containing runs that are ready, newly changed, or not yet evaluated; blocked runs retain only a dependency/version certificate. Do not retain an `Authority` between scheduling calls.
2. Observation identities by full RunID, ordered by observation ID; retain consumed identity/validation coverage separately. Associate changed observations with their actual target, not their hash prefix or payload. There is currently no subject-leading observation index in the schema (`store.go:110`): a new `WHERE subject=?` query would still scan the table. Use memory membership and primary-key point loads for selected/changed IDs.
3. Intent identities by source RunID and resource root; terminal obligations by full RunID; live delivery candidates ordered by the existing delivery key; unresolved and unknown memberships maintained separately. Settled operations leave the live candidate set, not durable history.
4. Root ID to profile-order rank; dirty root set; run-to-root and operation-to-root maps; scope-to-parent reverse edges for invocation dependencies. Root report order remains ascending root ID. For a root report, group intents by root once and keep charges as a derived report total or query grouped charges once per full report. Do not use that derived total in admission/reservation.

Initialization follows Create validation and successful commit (`store.go:506-522`), and follows Open's validation, epoch increment, and renewal-connection commit (`654-697`). In particular, building from Open's pre-increment report would capture stale epochs. Initialize candidates without speculative reduction of all runs: initial validation does not grant permission to reorder first-use reducer errors.

The smallest candidate structure can be a sorted set/slice of live/dirty keys with binary search and explicit O(frontier size) insertion/deletion cost; it must not be a bitset scanned over all retained runs every turn. Do not call this generally logarithmic or linear. For static B roots and a constant-size affected frontier this avoids the global retained-history loop. A balanced tree is only justified if actual frontier measurements require it.

## Exact mutation seam and fallback

Explicit deltas should report changed RunIDs, observation IDs, intent IDs, terminal obligations, scopes/roots, and profile/context invalidation. Mark identities dirty; load canonical retained rows at the next scheduling/report boundary. Only publish the delta after successful SQLite commit. No new SQL transaction may be introduced between a decision and its existing durability point.

`commitOwnedTx` is a useful seam (`store.go:222-237`) but is incomplete. The following writes deliberately commit directly while `ownerMu` is already held:

* `dispatch_admission.go:58`;
* `request_authority_admission.go:257`;
* `receipt_read.go:227,300` (the refusal branch can commit an adapter result).

Factor a non-waking commit-and-record helper under `mu`; preserve wake notification only at callers where acquiring `ownerMu` is already legal. Routing these direct commits through today's `commitOwnedTx` deadlocks. Create/Open initialize after their separate commits; read-only inspection/Replay commits do not publish deltas. All rollback paths discard the delta, including cancellation and commit-hook rejection. A committed conflict-evidence transaction can return `ErrConflict`: publish by commit success, not public-method return success (`receipt_conflict.go:133`).

Guard reuse with the pinned connection's `total_changes()` before starting any trusted transaction and before each cached scheduling/report read. Check before BEGIN, not just after COMMIT: otherwise a direct corruption followed by an ordinary admission gets silently acknowledged as trusted. Record a new watermark only for a completed, classified transaction whose starting watermark was trusted. A failure or rollback may conservatively dirty/fallback; it must never publish tentative identities. Counter retrieval after a committed write must not turn an already committed operation into a purported rollback; if bookkeeping cannot be completed, disable reuse and preserve the operation's original result.

For an unexpected write, permanently disable the affected optimization for this Store and execute the original traversal. Do not run an eager full validator at that point: the original traversal deliberately does not visit later corrupt programs before returning an earlier ready run. Reopen can regain optimized operation after its independent validation. This fallback is not an excuse to leave common ordinary mutation paths unclassified: count fallbacks, and require zero unexpected fallbacks in the qualified workload.

`total_changes()` is an anomaly guard, not a mutation log. It covers same-connection DML, not another connection or DDL; replacement victim deletes are excluded even though the replacement INSERT changes the total. Track main/temp schema cookies and the immutable limits/profile context too; disable reuse on schema changes and pre-existing or newly introduced triggers unless their effects are explicitly covered. This prevents a test trigger's extra writes inside an otherwise trusted transaction being silently covered by the transaction's delta. The existing full validation/ownership model does not support arbitrary concurrent hostile file writes or dishonest manipulation of SQLite schema cookies. If other-connection mutation detection is retained defensively, use `data_version` as a fallback signal, not an ownership guarantee. See [SQLite total changes](https://www.sqlite.org/c3ref/total_changes.html) and [data_version](https://www.sqlite.org/pragma.html#pragma_data_version).

An update hook on the existing driver supplies table and rowid but not a committed semantic delta (`go-sqlite3@v1.14.52/sqlite3.go:707-721`). It is called for tentative changes and cannot query the same connection from the callback. SQLite omits REPLACE victim deletion and truncate-optimized deletion; ordering relative to the write is unspecified. Thus a hook-only cache can retain a deleted identity forever. Hook rowids also need old-key handling for row/key replacement. See [SQLite update-hook contract](https://www.sqlite.org/c3ref/update_hook.html). If used, collect bounded invalidation notices only, drain after statement/transaction completion, and fall back on ambiguity. Explicit deltas are more source edits but expose the dependency contract for review.

## Required invalidators

| --- | --- |
| New/consumed observation, including approval, message, terminal and settlement admission | Validate the changed row with the existing observation checks before readiness traversal; dirty its full RunID; remove consumed candidate only after commit. A consumed corrupt row cannot disappear from validation coverage. |
| Run projection, sequence or epoch; subject generation, revision or retirement | Dirty run, terminal obligation, its root/scope and dependent invocation; subject change affects all retained generations. Reload authority immediately before selecting; Commit still checks equality/generation/retirement (`store.go:823-835`). |
| Program, limits, metadata/profile, template, binding, handoff evidence | Invalidate dependent readiness certificates, including previously absent bindings. Unknown direct changes take baseline fallback. Keep existing binding construction and handoff alias protection (`invocation.go:98-121`; `runner.go:348-379`). |
| Invocation admission, dynamic/static membership, retry successor | Add new run/observation/intent memberships; invalidate successful-absence entries; dirty ancestor scopes and root, and the original invocation delivery. Index by full RunID, never subject alone. |
| Intent or terminal obligation creation; ACK; settlement; outcome delivery | Add/remove the exact original delivery key and refresh unresolved membership. ACK and retained result are different facts. Keep terminal sequence/destination keys intact. |
| Reservation or allowed attempt | Refresh operation's unresolved/unknown report state and root charges. This cannot become permission to dispatch. |
| Valid external receipt, adapter result, receipt reconciliation result | Dirty operation, owning scope and all waiting ancestors; known result can unblock roots before settlement. Unknown becomes known only through original validators, not existence/count alone (`composition_reservation.go:124-137`). |
| Conflicting receipt retained | Preserve original winning outcome; refresh evidence-dependent views without treating the rejected receipt as settlement or replacing the first result. A failed public call may have durably appended evidence. |
| Freeze, closure, reply, child/root publication | Dirty exact scope and ancestor waiters. Closure/freeze precedence remains in `prepareCompositionScope` (`327-349`); reply admission precedes descendant/external outcome checks (`354-425`). A closure may unblock non-success without making external uncertainty disappear from reports. |
| Source authorization, delegation/revocation/request binding, dispatch admission, read ordinal/refusal | Invalidate relevant retry/preparation opportunities and report dependencies; do not store allowed/refused authority as reusable authorization. Existing final gate reads stay mandatory (`dispatch.go:90-147`). |
| Open/adoption, Close, connection loss, context/profile mismatch | Discard entire index. New owner independently validates and activates epochs; never transfer the previous owner's frontier. |

Root invalidation must follow ancestor dependencies, not just the run's immediate scope. A child publication can release a parent whose own run and root projection did not change. Cross-root lifecycle facts explicitly list both roots (`composition_facts.go:29-39,73-102`). Receipt-read outcome adoption must dirty the original operation's dependents as well as the resolver.

## Traversal semantics

Readiness: preserve `(subject,generation)` rotation after `last`, with `last` reset per Run, and first eligible observation by original ID. Skipping an unchanged blocked run is justified by a dependency certificate, not just `Status == open`. On a dirty run execute the original load/program/binding/Reduce sequence lazily at its original position. A newly changed observation validation error precedes candidate traversal just as full `readObservations` did. Do not eagerly reduce all dirty runs and return their first error out of rotation order.

Delivery: retain the same sorted delivery keys, internal/external category opportunity, per-Run `attempted` set, MaxInFlight/root limits and retry eligibility. Keep all unresolved external candidates eligible for reconsideration at each new Run; a prior Run's attempt marker must not suppress a later retry. A minimal frontier still enumerates live pending candidates each turn: bound/count that cost separately. Eliminating this additional cost under very large live frontiers requires further ordered/capacity-aware bookkeeping and is not a free consequence of eliminating settled intents.

Roots: process dirty roots in the profile's original order; publication remains immutable but related report uncertainty may change later. Clear a dirty bit only for the generation of invalidations examined. A concurrent Store operation may commit between PrepareRoot and SettleRoot; preserve the latter's independent transaction recheck (`composition_root.go:58-85`) and retain/requeue any newer dirty generation. Do not claim quiescence from an empty old frontier after a newly committed wake.

Full reports: keep report ordering, slices and errors. Copy any cached nested maps/slices before returning, so callers cannot mutate the Store's derived state. Independent read helpers for inspection remain full readers. The baseline pending-delivery and finish-report code iterates intent maps before sorting output; there is no deterministic first error among multiple corrupt intent-map entries. Preserve deterministic traversal/error boundaries and compare errors in fixtures with one reached fault; do not invent a stronger ordering claim for that map iteration.

## Smaller alternatives and compact output

Call-local grouping by run/root is immediately useful: it removes observation matching and root-by-intent products, and one grouped charge scan removes per-root charge table scans. It still reads all retained records on each turn/call. Mark this as a bounded partial correction, not the requested cross-call solution.

A root-only frontier can derive dirty root IDs incrementally from `composition_facts` using its existing integer primary key and `RootIDs` (`composition_store.go:19`; `composition_facts.go:29-39`). This is a plausible first stage with the same anomaly fallback. It cannot cover every ordinary observation/ACK path or substitute for the invalidation inventory, and it must not reread the complete fact prefix for every poll. It also does not eliminate a dirty root's repeated walk of a large frozen descendant set. Retain original preparation first and report that bound rather than constructing a second incremental execution engine.

Do not add compact report mode in the first structural patch. Existing qualification explicitly requires all B root reports, and callers/tests inspect OpenRuns, uncertainty and pending deliveries. There is a real separate use case: `examples/weather-agent/main.go:177` discards RunReport. A later explicit opt-in in existing RunOptions could omit expensive collections while preserving default output, but must state whether diagnostic validation/errors are still performed. It cannot silently skip receipt validation or call an omitted collection empty. The existing series comparison must remain full-report; compact mode would be a separately labeled workload/API-use comparison. Default full output still costs at least its serialized/copied bytes.

## Complexity claim permitted before measurement

Let N be retained state, U the changed rows/identities, F the live candidate frontier, D the total dependency scope revisited for affected roots/invocations, and Q the full report output size. Initialization is O(N) plus the unchanged full audit. Target steady-state discovery is proportional to U and affected frontier maintenance, plus D and existing transaction-gate work; full report materialization is at least O(Q). Sorted-slice frontier maintenance can be O(F), and sorting a newly built list O(F log F). Full grouped report scans remain O(N) until report state itself is incrementally maintained.

For the bounded series with constant-size affected scopes/frontier, this removes unrelated per-turn root/run/settled-intent work; B full reports containing B roots still require Omega(B²) output. Do not generalize that workload's bound to one huge root, large pending queues, retry storms, request-authority prefix reconstruction, or full snapshots. Measure rows/VM steps as well as SQL and Go visits: a point-shaped SQL query on an unindexed column is still a full scan.

## Decisive validation stages

1. Preserve baseline and interrupted prototype separately. Prospectively freeze the amended contract, exact deltas, fallback behavior, output contract and work counters. First add counters for global IDs visited, observations validated/matched, intent/root matches, root preparations, rows/VM/fullscan steps, dirty identities and fallback causes.
2. RED structural controls: after one initialization, call Run repeatedly on an unchanged large waiting/completed Store, then change one of B independent roots. Assert zero unrelated root preparations and no retained-history matching, excluding required full report copies/scans explicitly. Add one giant-root and large-live-frontier controls to expose remaining D/F costs rather than hiding them.
3. Introduce grouping/root frontier first with baseline differential output and error comparison. Existing `readiness_reuse_test.go:118-187,193-235,349-438` covers rotation, later corruption, context changes, retired generations and binding errors; `composition_inspect_test.go:393-505` covers new membership, late receipt before settlement and conflicting receipt. Preserve these semantics, including direct corruption fallback.
4. Add transaction delta publication and negative readiness/delivery reuse only after every writer and direct commit is classified. Test commit success with later returned error, no-op duplicate, rollback/cancellation, failed commit, unexpected DML before an ordinary transaction, DELETE-all, REPLACE collisions, TEMP trigger insertion, schema/profile changes, new generations and absent-to-present binding/membership. Verify failure does not poison other Stores.
5. Exercise receipts before settlement, closure versus freeze ordering, ancestor publication, terminal delivery ACK, unresolved non-idempotent effects, adopted results, revocation/request binding before final dispatch, and per-Run retry reset. In particular `async_reporting_test.go:18-67,70-99` requires a retained valid receipt to remain known after settlement failure and malformed receipts to remain errors. Keep stale authority rejection inside Commit/admission, not just in discovery.
6. Race controls interleave public admission, lifecycle changes and result accounting with each scheduling phase and root settlement. Assert dirty generations are not lost; account workers before final reports; preserve Close joining and lock order. Fresh-owner/SIGKILL/reopen/Replay qualification remains controller work on a frozen candidate.
7. Only after semantic and counter controls pass run the established serial timing campaign. Report unchanged full-report workload first, residual report/snapshot/gate costs separately, and every fallback. Independent adversarial review must approve the actual mutation inventory and measured evidence before claiming the structural correction complete.

Material stop conditions: inability to enumerate mutation coverage, changed authority/recovery gates, lost first-reached errors, silent compact output, hook-only correctness, a global scan disguised as a dirty-set refresh, or scope expansion into a general incremental scheduler. A partial root/grouping improvement is preferable to claiming these are solved without evidence.
