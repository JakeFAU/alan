# Phase 1D.1 dispatch and progress contract

Existing Phase 1D durable identity/authority/closure/replay rules remain binding. This increment changes automatic scheduling while network work waits.

One Run owns scheduling and its transport set; overlapping Run is explicitly rejected. The positive effective in-flight limit defaults to 2. Zero-valued Go options may select the documented default for compatibility; negative or explicitly nonpositive CLI values fail. A slot remains claimed through completion accounting; at most that many workers/candidates exist. Extra work stays in the durable ledger. The same intent is attempted at most once per invocation. Subsequent invocations may reattempt only under the existing endpoint profile and original key.

Reserve an intent claim and dispatch budget before launching network-only work. Immutable candidates carry exact intent/attempt/authorization descriptors; the owner revalidates them against retained records before receipt persistence and separate observation settlement. Authentic late receipts do not become stale merely because their physical epoch is old. No policy, identity or authority is created by goroutine startup or queue arrival.

Give local commits, internal deliveries/lifecycle work, completed receipts and available launches regular bounded opportunities. Skip saturated transports without waiting. No network/body read or worker-slot/completion wait holds a store-wide mutex or SQLite transaction. With no immediate work but owned requests in flight, wait for completion/cancellation rather than poll, and never report Quiescent=true. Quiescent with retained Unknown means this invocation has no eligible action, not application completion. Live completion ordering may vary; recorded observation consumption remains replayable.

MaxSteps bounds ordinary commits, including a committed transition whose post-commit observer returns an error; MaxDispatch counts reserved delivery/launch work once; in-flight capacity bounds simultaneous owned work independently. Handling a completion is not a second dispatch charge. Budget exhaustion stops new work and returns an explicit limit error without erasing authorized uncertainty or cancelling logical runs.

On cancellation, budget exit or fatal error: stop launches, cancel owned transport, account for received candidates with a separately bounded cleanup context or retain uncertainty plus explicit error, and join all workers before Run returns. Concurrent Close must coordinate rather than close a connection/release exclusivity under active owner use. The request timeout defaults to 2s; cleanup uses a separate five-second context. This is not a hard wall-clock bound: joining is mandatory and SQLite busy/commit work can outlast cancellation. No worker continues accessing storage after return. Timeout/cancellation is not proof of no mutation. Non-idempotent uncertain attempts are not blindly repeated; storage/corruption errors are not swallowed.

The decisive test requires exact endpoint-held acknowledgment before peer commit, peer result availability before endpoint release, and original settlement afterward. A real pre-commit pause may gate the peer until the endpoint is held; the controller may release that pause but cannot call Commit or manufacture state. Explicit acknowledgments establish order; watchdogs only fail stuck tests. Reject wrong request/process identities, early peer work, or response/timeout/cancellation before progress. Actual CLI and separate endpoint/store are required for subprocess evidence, including both-profile concurrent SIGKILL and received-but-unrecorded results. Prior accepted/rejected Retry, repeated restart, terminal recovery and replay-no-dispatch cases remain regressions.

No unbounded fairness, distributed fencing, business exactly-once or general production-readiness claim is added. Static grants, one PC per run and existing cross-store key limitations remain.

Concrete options selected by the implementer before qualification: Go `RunOptions.MaxInFlight` and CLI `--max-in-flight` (default 2); `ExternalTimeout` / `--external-timeout` (default 2s); five-second separately bounded durable cleanup. Shutdown tests qualify completion/error handling; an already dequeued candidate that cannot be persisted remains unresolved with an explicit error.

A capacity-one coalesced wake hint accompanies authoritative commits so concurrently admitted ordinary input can wake an idle Run. The hint carries no observation or decision; recovery and rescanning use the durable ledger. It does not add a second scheduler or an input server.

Active Store write transactions own their rollback explicitly. Their transaction-lifetime context is detached from caller cancellation after an initial check, while SQL statement contexts remain cancellable and the commit path checks cancellation again. This prevents database/sql's asynchronous rollback from discarding the pinned connection before received-completion cleanup. Cancellation before the final check aborts; cancellation racing after it may leave a whole committed transition. Partial state is never permitted. Create/Open retain their existing unpublished-store transaction behavior. The cleanup deadline is separate from the existing SQLite busy timeout; qualification states the actual bounded policy without treating timing as causal evidence.

The explicit synchronous DispatchExternal API remains available for controlled individual deliveries. The bounded transport set belongs to automatic Run; concurrent independent direct dispatch is outside that ownership contract. Each scheduler pass offers one completion, one internal delivery, one available launch and one round-robin ordinary commit. A retained uncertain non-idempotent attempt is skipped without a dispatch charge. Preparation that settles retained evidence or a denial counts as delivery work. Reaching a budget without further eligible work may quiesce; exceeding it to perform additional work is rejected.

UnknownExternal lists authorized outcomes with no retained receipt evidence. A valid durable receipt whose separate settlement is pending remains in UnresolvedIntents/PendingDeliveries, with the settlement error exposed; its physical outcome is already known. Malformed retained receipt evidence returns validation error rather than being classified as either known or Unknown.
