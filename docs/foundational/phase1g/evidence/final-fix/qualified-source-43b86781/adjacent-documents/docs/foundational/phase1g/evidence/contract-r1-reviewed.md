# Phase 1G bounded composition contract — revision 1

Baseline: `80dead19846d9b034b4457a9436e43acb81da3df` (merged main, inspected 2026-10-26). The 189 Phase 1F contributing source files retain source identity `2dacb402e50ee938d6184c14b40ba469fdcb8d91d9c30eac178b0dcb2a0fd3f8`. Historical records remain untouched.

## Decision and alternatives

A fixed reusable participant pool would retain constant subjects, but today's evidence helper is a one-shot composition of two programs. Safely reusing both requires invocation-scoped input, residual state, reply correlation, and either suspended frames or separate depth pools when parents wait. Repeating fixed helper graphs or unrolling one participant per possible item fails the request. This alternative remains appropriate for future long-lived services; it is not implemented here.

Implement bounded durable invocation of a retained **component template**, which may contain ordinary programs and internal ports. A template is immutable program artifacts, static relative wiring, a public request/result port, input defaults, and explicit permitted child templates/capabilities. Invocation supplies typed request data and a fresh identity. Scope binding resolves relative peers to the created executions and caller; it cannot grant arbitrary targets or effects. Artifact bytes and binding semantics remain locally available. The program and topology are not recompiled by Go or reprovisioned by the author after work becomes known.

This is genuinely data-dependent creation of logical executions within explicit limits. It is not unrestricted spawning, recursion, distributed ownership, or a new scheduler. The same `Store.Run` schedules all ready ordinary executions; its existing bounded adapter dispatcher controls physical external concurrency. Suspended parents own no dispatcher slots. Queued logical work may exceed physical capacity. Local reductions remain serialized finite commits.

## Ordinary authoring basis

Add bounded typed record lists (including bounded nesting where needed), value access/append and snapshot iteration. A runtime loop carries its finite cursor and collection snapshot durably. Each reduction is finite; iteration may span ordinary Receive/Request boundaries. Preserve old scalar representations and old artifact/history meaning.

Add an ordinary invocation effect and correlated invocation-result receive. Invocation intention commits through the same execution/intent protocol; separately authorized admission instantiates a permitted retained template and records its original accepted/rejected outcome. The caller receives the component's public response or a defined terminal failure/rejection. Retransmission of an existing operation cannot create another invocation. Source identity, generation, revision, operation and selected template are checked. Child policy is ordinary code, with no dispatch on component/role names.

A public reusable collection component derives scatter/collect behavior from these steps. Its author defines the item component once; the builder does not unroll items into helpers or fixed result slots. Input is an ordered typed list of records containing an explicit item ID and typed item input. Result is an ordered typed list containing the same IDs and outcomes. Empty input returns an empty successful collection. Duplicate payloads with different IDs remain distinct. Duplicate item IDs reject the whole work set. Over-limit input rejects before admitting any child work. Invalid UTF-8, nested bounds and arithmetic overflow reject explicitly.

The component's request/result schema is identical when direct or nested. Namespaces, invocation IDs, item IDs and worker/run identities are distinct. A new invocation begins fresh local state under a newly authorized operation; reopening an existing invocation preserves its state, budget, operations and observations.

## Durable boundaries

1. Transport admission retains the exact request and original run binding. Application acceptance is the ordinary commit consuming that validated request into the work-set projection. This is the durable work-set point: IDs, values, ordering and bounds are retained, and no planner reruns on recovery.
2. Ordinary iteration commits each invocation intent and pending correlation into the parent projection/history. No child can appear before its source intent commits.
3. Source authorization is retained separately. Invocation admission atomically retains its descriptor/result, child origins and initial executions, resolved bindings, permissions and root-budget charges. Repeating an operation returns this same result, including rejection. Cancellation before admission is revalidated against the scope closure rule below.
4. Children run ordinary programs and interact through their bound public ports. A public reply is retained and authenticated against the invocation endpoint/operation before the caller can consume it. Response recording and parent consumption are separate commits. Terminal failure cannot be reported as a successful item. No success is inferred from receipt absence.
5. Parent collection consumes each original operation result once, retaining item correspondence. Result order follows accepted input order, independent of completion order. Waiting for the next ordered result does not prevent siblings executing or recording their own results. Unknown required work leaves the aggregate pending.

All accepted invocation artifacts, inputs, bindings, results and budget charges are reconstructible. Replay validates creation origins and descriptors without creating runs, admitting work, calling adapters or planning. It has no dispatch registry/credentials. Live recovery may continue already eligible work and is labeled separately.

## Root budgets, closure and uncertainty

Each admitted top-level work obligation has one immutable resource envelope, inherited by all descendant invocations: total invocation admissions, total created program runs, maximum nesting depth, total external-effect authorizations and physical adapter concurrency. Component input list bounds additionally constrain each request. Root charges never reset on child invocation, nested calls, process death or reactivation. New effect authorization is charged once per existing intent, not per retry of the authorization API. Recovery configuration may not silently raise a persisted bound. Inspection exposes limits, charges, original IDs and unresolved evidence.

Qualification defaults: maximum input items 8; counts 0, 1, 3, 7, 8 and rejected 9; physical adapter capacity 1 and 2; maximum invocation depth 3 (root at 0); shared maximum 32 invocation admissions, 64 created program runs and 96 external effect authorizations. These are fixture/deployment bounds, not universal architecture limits. Test lower exhausted bounds separately. No provider spending is authorized by these work ceilings.

Cancellation is scoped closure, not group cancellation or compensation. CancelRun closes the addressed run; for a root obligation it also prevents further descendant invocation admissions and not-yet-authorized effects under that root. Already admitted descendants retain their execution records and may finish pure computation and deliver late evidence; already authorized external operations retain uncertainty and may settle. A closed parent never reopens or reports successful completion. Siblings and descendants do not silently become failed merely because their parent closes. RetireSubject remains distinct and prevents future generations. This profile implements no automatic descendant cancellation, reassociation or cleanup custodian.

Cancellation/admission and cancellation/completion races have serialized outcomes: admission first retains children/charges; closure first retains rejection and no children. Completion recorded first remains evidence even if its consumption is then prevented by closure; closure first may still retain authenticated late evidence bound to the old operation, without satisfying newer work. Scope checks must not erase existing source authorization. Tests distinguish authorized external work from newly requested work.

Unknown adapter outcomes occupy the original unresolved operation. They are neither automatically repeated nor treated as completed; independent eligible work continues within remaining dispatcher capacity. A fresh invocation is different work and must not reuse or replace an uncertain business operation automatically. There is no new business deduplication/compensation claim.

## Compatibility and exclusions

New artifact/binding/collection semantics and any persistence schema change are explicitly versioned. Existing scalar programs and histories retain their IDs and interpretation. Create continues to use schema 3 for legacy provisioning. Invocation-enabled provisioning creates schema 4. Open/Inspect/Replay support both layouts with explicit version branches, and schema-3 stores cannot acquire invocation features. There is no conversion or general migration. Unsupported versions and inconsistent descriptors fail closed. The implementation must document the exact version matrix before claiming compatibility.

No live provider calls in this increment without separately applicable model/credential/spend authorization. Controlled providers qualify execution, not answer quality. Do not alter Phase 1F prompts, corpus, evaluation grades or study ledger. No multi-host execution, ownership transfer, general capability delegation, unrestricted recursion, public SDK stability or UI.

## Acceptance and independent checks

Use an independently calculated deterministic work tree before evidence leaves. Exercise the same artifacts with different post-initialization work sets, more work than physical capacity, out-of-order completion, identical payload/different IDs, direct and nested composition under saturation. Reuse the existing two-program evidence helper as a leaf template through public APIs.

Actual subprocess SIGKILL tests synchronize at work acceptance, partial completion and recorded response before consumption. Add causal provider barriers for held work and independent progress; do not use sleeps to prove ordering. Retain late/stale/duplicate result attempts, unknown outcomes, closure races and boundary evidence. Independent monitors check identity, ordering, budget conservation, no uncommitted dispatch/creation, no premature success, and replay with no dispatch. Faulty variants must reach the relevant boundary and be detected by unchanged monitors.

Measure author code, constant template/provisioning size, admitted work/run/record growth, physical active count, latency and recovery outcomes. Retain original failures and exact input/source identities. Successful traces are reachability evidence; finite tests are not unbounded safety/liveness proofs.

## Reviewed refinement candidate: exact operational choices

This section resolves initial review R1–R6 and is normative where the earlier overview is less specific. The original draft and review remain in `evidence/contract-v0.md` and `evidence/contract-review.md`.

### R1: one provisioned resource root

Trusted deployment provisioning associates an immutable envelope with one declared generation-1 root execution. The envelope identity is `(store namespace, root subject, root generation, resource-profile version)`. The root accepts one work obligation in this profile; a new request does not create a new envelope. Nested invocation cannot choose or create a root. Every member created by one invocation inherits its parent's envelope and depth plus one. All template-internal members have that same depth; their own invocations increment it.

Initial statically provisioned root/helper runs are reported as fixed cost and do not charge the **created-run** or **invocation-admission** ceilings. One accepted Invoke charges one invocation plus all newly materialized member runs, in the same transaction as their origins. The root is depth zero. Rejecting a request creates an immutable result but charges neither admissions nor runs; work attempts/retained denial records still consume finite ordinary instruction/list/byte limits. A root with 32 admissions and 64 created runs never gains another allowance from a wrapper. A list accepted before a later budget rejection remains accepted; its collector returns an ordered rejected item outcome and ultimately a non-success aggregate with completed partial results.

External effects spend the root allowance exactly once at **attempt reservation**, after the separate source authorization and capability/schema checks, atomically with the root closure check and durable allowed attempt. Count adapter and legacy external effects, not ordinary messages or invocation intents. Source authorization alone is not a spent external reservation. Denied reservations retain a correlated negative result, consume no allowance, and do not stop unrelated scheduling. An allowed but unknown attempt stays charged. Repeated API delivery of the same intent reuses its decision. A subsequently reduced local program budget remains ordinary application state; the root limit is an upper resource ceiling, not recovery policy.

All invocation-owned runs and the resource-root run are generation 1 for this profile. `Retry` against any such run is permanently rejected as `invocation_retry_unsupported`, even if another grant would otherwise permit it. Explicit fresh Invoke is the only new invocation operation. Physical restart advances activation authority without changing generation, root, work item, pending operation or spent budget. Authorized `AbandonRun`, `CancelRun` and `RetireSubject` retain their distinct target outcomes and close the affected invocation scope; retirement additionally keeps its existing permanent subject rule. No reassociation or group cancellation is implemented.

### R2: outcomes, reply candidates and structured completion

A template declares all member runs required and exactly one public reply endpoint. Its immutable outcome envelope contains invocation operation ID, template ID, original caller/run, item correlation, status (`succeeded`, `failed`, `cancelled`, `abandoned`, `rejected`), reason, optional **public response** with an explicit presence flag, and original result identity. Missing response is not fabricated success/default data. Bindings exposed to ordinary programs include status and response-presence before payload use.

Public Send still commits an ordinary immutable intent. For a versioned invocation binding only, its designated caller-directed reply is a retained notification obligation: it remains eligible for authenticated admission after its source terminates, including failure/cancellation. This exception is limited to the immutable caller route and already committed public reply; it never grants external dispatch, arbitrary messages or new computation after closure. Existing unscoped message semantics are unchanged. Attempt/source authorization and reply admission remain separate records. An acknowledgment-loss retransmission returns the same candidate. A second distinct public reply intent is a protocol failure even if its payload equals the first; it is not transport duplication.

The creation transaction starts the outcome state as pending. On the first committed non-success terminal of a required member, atomically freeze the failure trigger and the IDs of public reply intents already committed in that scope. Close future scope admissions/attempt reservations. Existing descendants may drain. Resolve any frozen reply obligations through their normal admission path, then retain the non-success outcome with the sole valid public response if present. The failure trigger and frozen candidate set cannot change on subsequent callback/delivery order. A later response is late evidence only. In particular, the evidence helper's Send(`invalid_result`) followed by Failure retains that public diagnostic response with status failed regardless of delivery scheduling. If an internal member fails while the entry waits without a committed reply, the invocation can return failure immediately; it does not wait forever for the blocked entry.

Successful publication requires all required member runs to have committed success, exactly one valid public response, and every admitted descendant invocation and committed external obligation to have a known result. Neither pending nor unknown required work permits successful publication. A terminal-success scope without a response or with conflicting responses returns a protocol failure. A descendant failure/rejection is known evidence; ordinary application code decides whether it is handled, but any unresolved descendant evidence still prevents a success claim. Local malformed/corrupt records are explicit store errors, never invented item outcomes.

All scope failure and publication decisions are retained owner transactions with monotonically ordered decision identities; replay verifies their prefix facts, freeze sets and immutable results. Success waiting on a join is generic structured completion, not an application oracle: it cannot assess evidence support, choose retries or aggregate item values.

The derived collector returns one result per accepted item in input order. All succeeded outcomes produce aggregate success; any failed/cancelled/abandoned/rejected outcome produces aggregate non-success with the ordered partial public results and reasons. An item with no terminal outcome remains pending. A successful empty list has no invocations or external effects. Faulty ordinary code bypassing these rules is detected by independent contract monitors, never repaired by those monitors.

### R3: closure and the last authorization boundary

Root closure applies to all descendants; member cancellation/failure/abandonment/retirement closes its invocation and descendants, not sibling invocations. Normal member success closes only its own ordinary execution. An invocation's successful publication closes its scope after its structured join; it cannot have pending descendants at that point. Root successful terminal intent cannot create permission for further work; root publication still observes the join rule.

Invocation admission checks the source run plus every ancestor scope's retained closure inside its admission transaction, even if earlier source authorization was allowed. Root/ancestor closure before that transaction rejects admission; admission first preserves all its children and charges. Source authorization remains historically allowed rather than being rewritten.

External attempt reservation/debit checks ancestor closure in the same transaction that grants the attempt. Source authorization before closure but no reservation is denied after closure and gets its durable negative outcome. An attempt reserved before closure **may launch afterward** under its original reservation; an already-running physical process is not revoked. Restart uses existing unknown rules and does not launch a previously reserved unknown non-idempotent adapter operation again. Authorized/recorded work can settle after closure; none is refunded or rebound. Public reply notification obligations are the narrow late-evidence exception described above. Physical Run-context cancellation is not logical closure.

### R4: closed deployment authority and immutable binding

The deployment provision supplies a finite template catalogue and root allowlist plus explicit permitted effect capabilities. Each calling artifact declares its possible template IDs. Provision validates the transitive dependency graph, required artifacts, internal/entry/caller port schemas and template declarations before creating a store. Calls require both source declaration and root permission. Each child's effect declaration is checked against the root deployment allowlist before any child is admitted. No request payload can supply code, grants, peer bindings, a root ID or an undeployed capability. General delegation is excluded; templates are a deployment-approved closed graph.

Invocation ID is derived canonically from namespace and committed source intent ID. Member execution IDs are derived canonically from invocation ID and template-relative member name, with generation 1; identical inputs do not share identity. Bindings retain template ID, source artifact IDs, relative-member map and sole caller route under `alan/binding/v1`. They are separate immutable execution inputs; original artifact bytes/IDs never describe silently patched instructions. Pure resolution is performed identically for live reduction and replay from those retained bindings, while independent checks verify allowed endpoint relationships. No prefix substitution in user strings is permitted. Root and invocation IDs are not physical worker IDs.

### R5: capacity means physical owned work

Each root persists its maximum active external attempts. The existing Run owner maintains active counts per root and globally; launch requires both `active(root) < persisted root limit` and `active(total) < RunOptions.MaxInFlight`. Larger recovery options cannot raise a root limit; smaller options may lower actual concurrency. Local reductions use the same single owner; waiting logical invocations reserve no physical slots. Multiple roots share the global ceiling. Unknown remote activity is not claimed to have stopped when a returned unknown candidate releases its local slot.

At capacity one with one held transport, require independent pure computation, messages or child admission to progress; a second external transport must wait. At capacity two, require a second external leaf to finish while the first is held. For nested saturation, P waits on Q which invokes L; after releasing the earlier transport L must actually execute and return. A test-only variant incorrectly charging P a physical slot must fail the same causal progress monitor. Admitted/open invocation counts and physical active counts are reported separately.

### R6: finite values, residual iteration and compatibility

A collection is a typed native list of closed records, optionally with bounded nested list fields. The schema retains MaxItems, total canonical list-byte limit, element fields and optional unique string identity field. No arbitrary recursive type or cyclic value/schema is accepted. Maximum schema nesting is an explicit operational bound, distinct from invocation depth. Invalid UTF-8, extra fields, wrong types, duplicate keys and over-limit requests reject before application acceptance. Empty lists have one canonical encoding. Public constructors/accessors and retained artifact boundaries deep-copy data. Scalar encodings remain unchanged; structural list equality never depends on pointer identity.

ForEach captures an immutable snapshot and initializes its durable cursor in one ordinary commit. Advancing/binding the next element is another finite commit; the current element and body PC remain retained until subsequent body steps commit. A crash between binding and Invoke resumes the same element's body rather than advancing again. Invoke stores its pending identity and specified state updates atomically with its intent; later append/cursor commits cannot erase that obligation. Append checks the declared element/key/count/byte bounds before changing projection and rejects overflow without partial data. Indexing outside the snapshot fails explicitly. A body mutating another list cannot change the captured snapshot. Zero iterations do not establish variables assigned only in the body. Nested loops have independent compiler-owned residuals.

New collection/invocation artifacts use `alan/1g/v1`, compiler `alan/author/v2`; ordinary legacy compilation remains `alan/1e/v1` / `alan/author/v1` with identical bytes. New metadata is omitted when absent. Legacy semantics reject collection instructions/values rather than silently adopting them. Scoped invocation binding is explicitly versioned even when its retained member artifact uses legacy scalar computation. Schema 3 remains the unmodified legacy layout; invocation-enabled stores use schema 4 and external key version 2. Open/Inspect/Replay choose the corresponding validation path without conversion; unknown schema/binding/program versions fail before activation. Replay checks both directions of origins, child membership, grants, result decisions and conserved charges, never creating missing records.
