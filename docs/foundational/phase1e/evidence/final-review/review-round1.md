## Findings

### FR1 — P2 / Important: explicitly nonterminal output messages become validated success

**Locations:** `adapters/openai/openai.go:196`, `adapters/openai/openai.go:232`, and `adapters/openai/protocol.go:24`.

The decoded output item retains only Type, Role and Content. Its recognized protocol `status` is ignored. Therefore this exact controlled HTTP response is accepted as `Disposition: validated` with payload `answer: candidate`:

```json
{"id":"probe-id","model":"fixture","status":"completed","output":[{"type":"message","role":"assistant","status":"incomplete","content":[{"type":"output_text","text":"{\"answer\":\"candidate\"}"}]}]}
```

Changing only the message status to `in_progress` has the same result. The completed-message control also validates. Each case uses the actual OpenAI Prepare/Execute serializer/parser and exactly one loopback HTTP contact. No live provider or real credential is involved. The diagnostic output preserves the original response alongside the returned candidate.

**Why it matters:** requirements section 6 says incomplete outputs must not become success. A contradictory envelope is still invalid provider evidence, not permission to publish its partial/nonterminal message as complete. `effects.Result` trusts `Disposition: validated` after checking the payload schema; thus ordinary application `valid` checks do not repair this missing protocol validation. A syntactically complete JSON payload does not override an explicit incomplete message status.

**Primary protocol support:** the official [Responses create reference](https://developers.openai.com/api/reference/resources/responses/methods/create) documents the output-message status alternatives `completed`, `incomplete` and `in_progress`; the [Go Responses reference](https://developers.openai.com/api/reference/go/resources/responses) exposes the corresponding output message type. Checked 2026-10-25. The large create page exceeded browser fetch size, so its official search-extracted schema was consulted. This review does not claim the live provider was observed returning the contradictory combination; it establishes a concrete parser/fail-closed counterexample inside the controlled protocol-validation contract.

**Recommended correction:** inspect status on accepted output item types and reject an explicitly incomplete/nonterminal/invalid status before admitting a successful payload. Extend exact protocol-key handling for the newly consumed status field so `Status`/Unicode case-fold aliases cannot override it. Retain the original raw evidence with a nonsuccess disposition and no hidden repair/retry. Cover the exact two original bodies, completed control, present malformed/null/unknown status, alias conflicts, and the allowed reasoning-item shape. Where an accepted reasoning item supplies status, handle an explicit nonterminal status consistently rather than silently ignoring it.

**Compatibility recommendation:** preserve absent item status as the existing explicitly documented compatibility subset, provided the top-level response is completed and all other checks pass. Current controlled fixtures omit it, and this finding does not require inventing a mandatory-field migration across those fixtures. Treat missing and present-but-invalid as distinct cases, and document/test that choice. If stricter mandatory output-message status is intentionally selected instead, state that contract change and update the exact positive inputs; do not silently recast their previous behavior.

**Exact evidence:** `.superpowers/sdd/00-plan/evidence/final-review/probe.go`, `probe-output.jsonl`, `protocol-status.md`, and `original-source/`. The latter contains the original OpenAI source files and the complete frozen source archive/manifests, saved before any fix. Reproduction and exit semantics are in `commands.md`. The probe exits zero as an observation tool; its final two records explicitly demonstrate the defect. No source fixes were made by this reviewer.
