# Phase 1F frozen evaluation protocol

This is a bounded synthetic readiness exercise, not a production readiness determination. The complete corpus has eight documents and 25 newline-delimited statements. Development and heldout each contain four questions: one supported, one ambiguity, one missing-evidence and one contradiction case. Every question has two substantive aspects. The evaluator authored the sources, questions and atomic gold before seeing application implementation or outputs, after reading the approved plan and existing public evidence/lookup contracts only.

## Inputs and source identities

`corpus/manifest.json` lists document ID, relative path, version, SHA-256, byte size and one-based line numbers with zero-based UTF-8 byte spans. Load the exact file bytes as evidence assets using the manifest ID/version. The runtime version is the lowercase hexadecimal SHA-256 of those exact bytes, as required by `effects.NewAsset` and `Asset.Check`; it is not the document's editorial revision. `editorial_revision` separately retains the source revision label 1. Citation versions must use the runtime content hash. Do not concatenate documents, renumber spans, prepend titles, strip newlines or transform whitespace. Each line is below the current 2,048-byte lookup limit. The public helper returns one best matching line per query; it cannot retrieve an entire packet in one lookup. Questions remain well defined independently of this retriever.

`development-inputs.json` contains a `cases` array of `{id, question}` records. These are the complete runtime question inputs. `development-gold.json` adds case category, two aspect labels, acceptable semantic modes, atomic required facts with source references, illustrative forbidden claims and an explicit stopping rule. A required fact applies to all acceptable modes unless `required_for_modes` is present. Gold is an evaluation oracle and must never be included in model input. Heldout inputs use the identical input schema; the corresponding gold uses the identical gold schema.

The heldout materials reside in the plan's sealed-evaluation directory. Only the independent evaluator/reviewer may read that directory before unsealing. Sealing is a workflow access boundary, not encryption or an operating-system isolation claim. Corpus content is intentionally public for both systems; it does not disclose which heldout questions will be asked. The public freeze manifest commits to a sealed manifest hash; that manifest commits to the exact heldout bytes.

## Run design and fairness

1. Verify the frozen data with `python3 docs/foundational/phase1f/evaluation/verify.py` from the repository root. `--sealed` additionally verifies the sealed files and is reserved for an independent evaluator before unsealing.
2. Develop with public inputs/gold only. Freeze source tree, prompts, model identifier, adapter configuration, baseline definition, case order, effect/token/time/money limits and output normalization before unsealing. Record exact source and configuration hashes. A one-question evidence helper is the simple baseline; additional model/lookup requests used by investigation must be reported, not hidden as equal compute.
3. Both systems receive identical question bytes, corpus bytes, model configuration and evidence policy. Run each case once per system unless repeats and budgets were specified before the seal opened. Randomize or counterbalance system order if feasible and retain the order/seed; with four heldout cases, order effects remain a limitation. No outcome-dependent retries. Unknown provider outcomes reserve possible spend and cannot be silently rerun. Operational failures stay in the denominator.
4. Investigation scope is two evidence questions per round and at most one authorized revision. One-shot baseline and investigation have different call opportunities; compare actual usage and quality separately. An answer may use a single line for both aspects where the source supports this. There is no required investigation win, revision or minimum number of citations beyond what supports the answer.
5. The parent records a source/prompt/configuration freeze artifact. The independent custodian checks this artifact and the sealed commitment, then publishes the original heldout inputs and gold without alteration. Make inputs available to the runner; keep gold away from inference and unblinded implementation changes. Preserve timestamps and hashes of unseal/publication. Any later source or prompt change invalidates the heldout run as a blind evaluation; label reruns exploratory.
6. Preserve initial candidates, final responses, all cited spans, review decisions, round counts, provider results, pending/unknown IDs, elapsed time and available usage. Grade output without system identity when practical; reveal identity only after grades are recorded. Do not discard incomplete or unsuccessful runs.

## Output normalization and independent grading

The controller may normalize a result to JSON with `case_id`, `system` (baseline/investigation), `execution_outcome`, `initial`, `final`, `revision_count`, `application_review`, `elapsed_ms`, `usage` and `run_identity`. Each candidate has `disposition`, `answer` and `citations`; a citation has `document`, `version`, `start`, `end`, `snippet`. Preserve original raw output alongside this normalized view. If the baseline emits flat citation fields, wrap them as one citation. Unavailable initial candidates, usage or latency are `null`, not zero. The raw application disposition does not determine the semantic grade.

An independent grader first splits the answer into substantive atomic claims, records exact answer text supporting each match, checks each claim against the entire frozen corpus, and maps it to applicable required facts. Record `supported`, `contradicted` or `missing` per required fact and separately mark unsupported extra claims. Numeric comparisons are semantic: “exceeds” is strict greater-than, not greater-than-or-equal. Exact duration, unit, deployment condition and rollback version matter. Equivalent wording is acceptable. Document claims of no recorded decision do not entail that no decision exists elsewhere.

Next validate citation bytes, then evaluate claim-to-citation entailment. A correct fact with a wrong or absent citation can receive support credit but fails evidence coverage. Both sides of a conflict and their equal authority must be evidenced for a cited conflict claim. The canonical gold references are sufficient references, not an exclusive allowed-citation list: exact subspans or multiple spans that genuinely entail a claim can count. References to irrelevant exact bytes do not count. The source packet header makes the deliberately equal authority and common version/window explicit, avoiding a hidden latest-version selection puzzle.

Use `rubric.json` to report support recall, substantive-claim precision, citation validity and coverage, stopping/abstention correctness and revision change as separate dimensions. A targeted ambiguity clarification may correctly stop without answering the known rollback; this is expressly allowed in those cases. If it elects to provide an answer, the conditional answer requires both branches and the common rollback. For missing-evidence and contradiction cases, blanket refusal loses known-fact credit. Do not infer an epistemically correct abstention from an operational failure label.

A model or the application's reviewer may assist but cannot be the sole oracle. An independent evaluator must check the frozen atomic claims and byte spans, record reasons and adjudicate disputed entailment with a second independent reviewer. Keep application review approval distinct from external quality. Retain initial and final grades; a revision can improve, regress, be mixed or be unnecessary. Durability/replay assertions require their own evidence and are never inferred from an answer grade.

## Limits and fixture history

This is eight authored cases, only four heldout, with no statistical power or domain representativeness claim. The heldout cases use related readiness templates and different entities/values; this primarily tests transfer of the frozen rules to new instances, not broad generalization or resistance to benchmark contamination. Public corpus inspection may reveal likely tasks; the seal prevents direct question/gold tuning, not inference from readable sources. Absence is explicitly recorded in this corpus; this does not test discovery of absence in a large open corpus. The retriever is lexical and single-line; vocabulary and line layout affect results. One supported packet places both aspects on a single line, while others require combining lines. This heterogeneous layout avoids structurally requiring the larger system to win every case but is not a controlled ablation.

The evaluator did not run paid inference or inspect application outputs. No result, model availability, cost, latency or efficacy is claimed at fixture freeze. Validation checks structure, byte spans, category coverage and lexical reachability; it cannot establish model performance. Freeze revision 2 corrects an independently detected asset-version contract defect: revision 1 used editorial version 1 where `effects.Asset` requires the SHA-256 of the content bytes. Original public files and their manifest are preserved in `history/v1-public.tar.gz` and `history/v1-freeze-manifest.json`; `history/v2-correction.json` records the finding and byte-change scope. The independent custodian also retains the full original public and sealed material privately. Corpus/question bytes and semantic gold are unchanged. The defect was found before application implementation/output, with no heldout disclosure; the corrected fixture has a new identity and is not relabeled as the earlier freeze. Any later correction must similarly preserve old/new bytes, identities, reason and contamination impact.
