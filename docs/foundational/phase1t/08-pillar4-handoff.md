# Pillar IV handoff: when can a mutating attempt actually launch?

Begin with the manuscript's Cancellation–Authorization Dichotomy (Theorem 5.1 in the TeX/PDF, labelled `thm:dichotomy`, and Theorem 5.4 in the Markdown). Its second clause speaks about a *launch* after cancellation, even for an idempotency key. The running system separates first source permission, reservation of a particular attempt, transport-worker exposure and the endpoint's application. Determine which ordering statement each public path supports. Enter the investigation with the launch-level claim open.

## Frozen distinctions for the next study

| Cut / observation | What to establish from each path |
| --- | --- |
| Intent commitment | One retained local Emit records the exact payload, logical operation and original source identity. No transport or world mutation follows from this fact alone. |
| First permission | AuthorizeIntent samples current source generation, revision, status and applicable operation-specific exceptions and retains an immutable result. A later lookup returns that row. This differs from a fresh check of enclosing scope and charge at reservation. |
| Reservation | For an external intent, prepareExternal combines the saved permission, deployment grant and compositionReservationDecision before recording the attempt and applicable charge. The adapter path separately performs trusted bounded pure Prepare, checks the prepared request/grant, and retains its own reservation. Verify which resource profile is active. The current enclosing-scope check is conditional on composition membership. |
| Actual launch and application | A separately scheduled worker invokes HTTP exchange or the registered adapter Execute. The process can stop between durable reservation, worker scheduling, transport, and endpoint application. Identify the exact event called launch and observe it on the transport side. An allowed attempt record alone cannot timestamp that event. |
| Authentic late evidence | Correlate endpoint receipt or typed adapter response to the original namespace, key, source/generation and actual reserved request/attempt. Check how conflicting or malformed evidence is retained or rejected. Cancellation of a waiting run does not erase an earlier authentic observation or reopen that continuation. |
| Settlement and consumption | Establish which retained transaction records the receipt/result, which records delivery/settlement, and which actual live continuation, if any, can subsequently consume it. Include the closed/cancelled source case. |

## Smallest decisive experiment

Use one ordinary source issuing one intent, a separately authorized operator, and a deterministic local endpoint with a persistent count of applications. Use the existing private fixtures for barriers and the public Store for original operations. Independently record first permission, reservation/charge, worker entry, first endpoint receipt of a request, application and local receipt recording. Exercise an external request and a controlled adapter separately. Compare cancellation of the *actual source* to closure of only its enclosing root while the source remains open. A third comparator is the phase 1S/1T valid bound internal reply: its post-End exception concerns internal evidence and does not license launching a world mutation.

Freeze at least the following cuts: cancel before first permission; allow first, then cancel before reservation; reserve first, then hold the worker just before transport, cancel, and release; hold an authentic response before recording, cancel, then account; reopen a store with an existing reservation and no receipt. For the last cut distinguish idempotent and non-idempotent endpoint profiles, and separately test the adapter's existing-attempt/no-result policy. Verify that the actual cancellation occurred before the event being tested, preserving the retained allowed/denied reason. A historical allowance, an elapsed timeout and an endpoint that happens to deduplicate are three different observations. The smallest refutation of a universal no-post-cancellation-launch claim is one legal ordered prefix exhibiting an actual first/new launch after the relevant cancellation. An earlier launch finishing later does not refute it.

**Knowledge passed to Pillar V.** Suppressed requires evidence that the relevant mutating attempt could not be sent under the trusted dispatcher and the declared fault model. Unknown records missing outcome knowledge after a possibly effective reservation/launch; it justifies neither a success nor a failure conclusion. Known requires authenticated, correlated evidence of what the endpoint actually accepted/applied; settlement and consumer readiness are separate. A new execution-generation key need not deduplicate the same business request. State assumptions about trusted dispatch, endpoint idempotence/key scope, durable correlation, receipt authenticity, and the operator's actual scope before proposing recovery equivalence or a retry. The first Pillar IV task is to establish or narrow this protocol statement. The E=0 tree campaign supplies no result about these external mutations.
