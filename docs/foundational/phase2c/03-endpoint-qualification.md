# Independent application ledger qualification

The controlled endpoint produced three different observations for one namespaced non-idempotent original key across independently serviced packets. Before the original applied it returned `not_found`. After one application it returned the stored bytes and that application's immutable receipt. After a second actual application of the same bytes it returned `conflict`, count two, with no selected receipt. A separately applied operation with the same delta did not satisfy the original query. Both the counter adapter and the raw extended mutation format bind their actual body bytes. The endpoint and client share the Go wire contract. Reading their agreement as independent verification of the decoder would overstate the experiment.

| Concrete intervention | Observed boundary |
| --- | --- |
| Run two fresh format 2 ledgers in the same process with identical service order for independently supplied business packets. Send a lookup to only one ledger after each of five cuts. | Every column of `keys`, `contacts`, `applications` and `application_wires` compared equal after each cut. Reads only advanced the separate audit. The two same-key non-idempotent contacts actually applied twice. This directly exercises the endpoint outside the Store's separate ordinal policy. |
| Apply one keyed operation twice, then an unrelated operation, close and reopen the original database with a different process token. | Lookup returned the first receipt's mutation number, total and original process identity together with the exact leading/trailing whitespace on the received wire. Re-applying the same decoded request with different whitespace failed. Looking up its changed wire returned one same-key conflict. |
| Start three real CLI subprocesses successively on one host and port. The initial endpoint applies once, the successor opens the same ledger, the replacement opens a fresh database. | SIGTERM shutdown exited normally at each change. The successor retained both URLs and ledger ID and returned the receipt with the first PID. The replacement rejected the old route, and rejected the old ledger identity in a query sent to its new route. The genuine original ledger retained one application, one business contact and one query audit. |
| Send GET, query suffix, escaped path, lookup body to the apply handler, mutation body to lookup, or a POST to legacy `/apply` on the opt-in process. Return a 307 redirect to the application route to the reader. | No route-confusion attempt registered another application. The actual controlled reader made one contact and did not follow the redirect. Direct ordinary `Reader.Execute` produced a local refusal without a contact. |
| Return malformed, oversized, and length-truncated response bodies. Alter snapshot fields, source component identities, wire preimages or schemas in negative inputs. | No valid snapshot resulted. Transport truncation, protocol errors and endpoint conflict have different outcomes. The versioned resource rejected the other resource format in both directions. The four inherited fixture tests still passed. |

The endpoint suite completed **35 assertion-bearing leaves in each of normal and race mode**, excluding the subprocess entry helper. No test was skipped. The focused vet command also passed. For each command the recorder includes actual argv, environment, exit, complete Go output, source inputs, and executable identity. Format 2 has new tables and exact wire requirements. A format 1 database has no supported original-receipt import. These tests cover an honest unchanged ledger under the coupled service premise, including genuine independent process replacement. They do not qualify hostile responders or cloned/rolled-back ledgers, runtime read authority, actual consumption or executor crash recovery. The base rejected the new CLI flag. The first compile probe lacked the proposed APIs. The initial HTTP probe could not bind a sandboxed socket and was rerun with loopback permission. An initial restart test observed SIGTERM termination instead of the required clean return. The opt-in server now arranges signal handling before announcing readiness and drains active HTTP service on orderly shutdown.
