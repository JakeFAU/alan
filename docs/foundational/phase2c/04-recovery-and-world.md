# Process recovery and independent application

A reopened owner with separate read and adoption authority recovered one missing original counter result from an identified application receipt. In the positive histories the original source had already succeeded, its captured result was missing, its aggregate had not published, and the successor obtained Q for that source generation. The final parent's retained history selects both the invocation publication and the resolver's ordinary message. Its decision `applied` depends on the matched target, original issuance, receipt values and adoption. The endpoint retained one original business application. These are bounded implementation results for the frozen single-host and controlled endpoint profile. [Contract](01-contract.md) · [Process matrix](01-process-matrix.md)

## Reading the histories

Each case directory contains ordered `transcript.json` events, an endpoint journal and coherent local and world SQLite backups at named cuts. Every replay window has `<cut>` and `<cut>-replayed` backups and journals. The Go checks compared complete public Store inspections, endpoint inspection and byte-exact journals across replay. The raw backups permit an independent check of table contents. Process start records bind the executable hash, build information, source manifest, selected environment, PID and barrier configuration. The controller waited for a matching cut before sending SIGKILL and checked the kernel exit status. In held-packet histories, the executor acknowledged the closed source through its command pipe while the separate endpoint held the identified original packet before Apply. ## Ordering ingress before original closure

Independent inspection of the held captures from harness commit `f5728074` identified an ordering gap. Their endpoint ingress acknowledgment and durable terminal source observation both preceded SIGKILL. The controller could first observe the terminal state after ingress even when the source had already closed. Those captures establish an accepted packet surviving death and applying after successor Q. They leave the relative order of ingress and original closure open. [Earlier retained-absence history](evidence/process-normal/held-retained/transcript.json) · [Earlier lost-absence history](evidence/process-normal/held-lost/transcript.json)

The corrected histories independently held the endpoint at `resource.ingress/pre-apply` and the issuing member at `execution.staged/terminal`, inside its uncommitted End transaction. After the endpoint acknowledged the exact original key, the controller checked the staged member against the run and generation of the actual committed adapter intent. At the `ingress-before-R` backup this source remained open at sequence 5 with the genuine original ID, the original ingress was already journaled, and the application ledger was empty. The controller released only End, observed the same generation succeeded at sequence 6, then killed its owner. The separate endpoint remained held through fresh-owner Q and the first absence. These reruns supply the stronger ingress-before-R claim for both the retained and lost absence cases. ## Executed qualification

Each regime passed **12 histories, 28 Store owner processes, 16 acknowledged executor deaths and 30 replay windows**. Go reported 9.749 seconds normally and 52.261 seconds under the race detector. The test binary launched itself as a fresh executor, and the harness built the independent endpoint with matching race instrumentation. The commands used the local toolchain, CGO, offline modules and readonly module mode. The normal and race records include the exact invocation, source inputs and output. Their source inventory also includes the separate module's `consumer/commands.go`, which changed after capture. It is outside the dependency graph of these process binaries.
