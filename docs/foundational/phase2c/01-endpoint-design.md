# Controlled application ledger and receipt query

## Source and scope

At the Phase 2B base, `examples/effectboundary.Counter` sends exactly `Prepared.Wire`, a JSON encoding with `Key`, `Profile`, `Delta`. `internal/executor.externalRequest` and `exchangeExternal` send the full marshaled `fixture.Request` including original authorization, generation, epoch and sequence. The independent legacy fixture stores a re-encoding of decoded fields. Its `applications` contain the key and original receipt but omit the original wire. The no-channel counterexamples and old `/apply` remain in their historical domain.

The question here is whether a separate read can distinguish zero, one, or multiple matching committed applications at a snapshot, without changing which business packets apply or what receipts they generate. Assume an honest bounded local endpoint, unmodified durable ledger, a trusted deployment of the declared adapter and sole Store ownership. The URL and SHA-256 fields provide correlation under those premises. A copied ledger that deliberately diverges under the same identity, a rolled-back ledger, an imposter speaking the protocol, or forged SQLite rows are outside the endpoint trust premise.

## Routes, startup and bytes

`alan-resource --receipt-ledger` opts into resource format 2. A new empty database generates a 256-bit random identifier on first initialization. The database owns this identifier across restarts. The ordinary format 1 and opt-in format 2 reject each other's files. The opt-in process announces `URL`, `LookupURL`, `LedgerID`, `Store`, `Token`, and `PID`. Its only application and read routes are respectively `POST /phase2c/<ledger>/apply` and `POST /phase2c/<ledger>/lookup`. The lookup client uses only the latter, with redirects and automatic replay disabled. Each URL is a canonical literal loopback HTTP authority with explicit port, exact path, lowercase hex ledger ID, and no alternate escapes, credentials, query or fragment. Wrong methods and routes are rejected before selecting a handler. HTTP method alone carries no recovery privilege. `--response-mode finish-accepted` transfers a validated original packet to the endpoint's normal independent service lifetime. `drop-after-commit` applies to the mutation response only.

The ledger decodes a complete bounded original body (8,192 bytes) and retains the **received bytes** on every accepted mutation contact. A business-key reservation binds exact bytes, and a successful new application records a foreign-keyed application number, key and original bytes in the same SQLite commit as its immutable receipt. Keyed re-exposure of identical bytes returns the original receipt without a new application. Identical non-idempotent re-exposure can produce another actual application. An altered body for an existing key is a parameter conflict. No existing format 1 record acquires a wire preimage. A lookup's application comparison uses these retained bytes independently of the request digest, original `Prepared.Digest`, or current counter total.

## Public deployment and runtime integration

`adapters/receiptquery` supplies `Counter{Endpoint,Mode string}` and `Reader{Endpoint string}`, plus `CounterInput()`, `CounterOutput()`, `ReadInput()`, `ReadOutput()`. A controlled `phase2c.counter` / `phase2c/counter/v1` preparation checks the actual retained input/output schemas (delta int → mutation and total int), key, delta 1 or 2, selected mode and exact route. Its original wire is the three-field JSON described above. `CounterPrepared(p effects.Prepared) error` rechecks the full original preparation against that narrow profile. A missing result may be reconstructed only for mode `success`, using the exact original application receipt's `Mutation` and `Total`. Other modes and raw external operations can obtain application evidence but have no success reconstruction rule here. A reconciled result has no original HTTP metadata. Receipt wire fields are `Key`, `Profile`, `Delta`, `Mutation`, `Total`, `Process`, `PID`.

The distinct `phase2c.receipt-read` / `phase2c/receipt-read/v1` preparation accepts exactly `target` (string, 1,024 byte bound) and the closed output schema `status` (string, 32 bytes), `target` (string, 1,024 bytes), `mutation`, `total` (ints), `adopted` (bool), `adoption` (string, 128 bytes). Its logical `Wire` is empty. Its ordinary `Execute` refuses all requests. The opt-in Store path checks the concrete trusted Reader, authenticates the original held target and exact grants, then reserves a physical ordinal before calling `Reader.ExecuteRead(ctx,p,q)`. Any ordinary adapter with the same name, method, payload, URL or claimed protocol is insufficient. A read-only success can report a real receipt even when import is refused. The runtime supplies the final adoption disposition after durable accounting.

`EndpointID(endpoint,verb string)(string,error)` accepts only `apply` or `lookup` as the required final component. `LookupEndpoint(applyURL string)(string,error)` returns the corresponding lookup on that exact authority and ledger. The Store derives `Query` from retained facts. Its fields are `QueryID`, `QueryKey`, `TargetID`, `TargetKey`, `LedgerID`, `Wire`, `WireSHA256` (strings) and `Ordinal` (int, 1 or 2). Key tuples bind their own IDs under one namespace, and original and read IDs differ. `Wire` is the precise original adapter `Prepared.Wire` or the full marshaled allowed raw `ExternalAttempt.Request`, including its retained authorization/epoch. The prepared digest and wire SHA-256 remain distinct. The endpoint can verify an exact byte/key comparison. Only the Store knows whether the claimed target was committed and allowed in the indicated run, and whether the resolver may read or adopt it.

## Snapshot and noninterference

Use closed single-value JSON bodies with bounded UTF-8 and fixed field names. The physical query wire is the canonical JSON encoding of `Query`. A successful response encodes `Snapshot{Query Query; Number int64; Status string; Count int64; AppliedWire string; Receipt *Receipt}`. One service takes the ledger's resource mutex and opens an SQLite transaction, reads all applicable evidence for the original key, assigns the next positive snapshot number, and appends the query and complete response to its separate audit table. Commit linearizes that matching snapshot with respect to mutation commits. A repeated physical contact with the same identifiers has its own snapshot number. Unique logical retention and ordinal permission belong to the Store. The audit table and optional exact ingress/result append-only journal are outside the business projection. A held pre-application packet owns no lock and a lookup can therefore finish before its later application.

* Zero application rows for that key give `not_found`, count zero, empty applied wire and nil receipt. A later application is possible.
* Exactly one application with byte-equal wire gives `found`, count one, the business row's stored wire and its original immutable receipt. The receipt can identify an earlier process.
* Any same-key mismatch or multiplicity gives `conflict`, the positive number of applications by key, empty applied wire and nil receipt. No arbitrary receipt is selected.
* Malformed, truncated, oversized, redirected, non-200 or unbound responses give no authentic snapshot. `DecodeSnapshot(q,response)` verifies the entire canonical message, exact query correlation, bound wire and receipt, status/count structure, and endpoint bounds. `Reader.ExecuteRead` exposes the actual HTTP status and bounded received response on the ordinary query candidate; protocol/transport rejection cannot supply business evidence.

Under a coupled order of independently serviced mutation packets, deleting an arbitrary query commit deletes only a distinct snapshot/audit record. The query neither calls the mutation handler nor reads a business key for update, inserts a key, appends a business contact/application, changes a counter, cancels a held packet, or returns a replacement mutation instruction. Induct on mutation commits: their input, previous key/receipt set and total remain equal on both projections, hence so do returned keyed receipts and new business rows (with matched endpoint process identity). Read scheduling may move a real concurrent application earlier or later relative to the observation. Eventual service/termination is a separate premise.

## Directed attacks

Check original and lookup wire independence under whitespace variations and conflicting same-key bytes, authentic duplicate non-idempotent applications, immutable first-receipt total after unrelated mutation, provisional absence then found, double-keyed contact once-applied, redirect to mutation route, wrong method/escaped path, malformed/oversized/truncated snapshot, frozen mode/schema mismatch, exact bytes, and command restart with same or different durable ledger at the same address. Verify independent business tables before/after reads. Separate executor tests cover source identity, denied/unsupported attempts, authority, allowance and immutable settlement. These are prospective checks until the qualification names executed artifacts.
