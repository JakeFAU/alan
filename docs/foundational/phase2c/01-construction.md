# The original operation reaches the resolver before publication

**Question.** Can ordinary computations carry a committed mutation identity across the boundary of its captured invocation while its result is still missing? The first baseline answered only the static-wiring part. Its source committed exactly one request. The parent consumed the resulting ID in an ordinary message, echoed it, and stayed open. The source selected that ACK before End. The public host subsequently obtained source Q and replayed the Store. On that same source the ordinary single-port template constructor rejected the independent caller port with `extra caller boundary`. An earlier malformed template used nil initial data and reached only `missing data`. We retained its output separately. [Static observations](evidence/construction/static.json) · [Original Store](evidence/construction/static.sqlite.gz) · [Rejected precursor](evidence/construction/rejected-missing-data.json)

The existing outgoing public reply of an invocation goes through `compositionReplyBinding` and enters `composition_replies`. `prepareCompositionScope` withholds public success until all captured external results exist. A second receive on that port expects the original invocation request, already consumed. Within the old closed-template grammar there is no second ordinary message path from its members to a static outside resolver. Invoking a descendant resolver can pass the ID inward. Until its result publishes, the enclosing success has an outstanding descendant, checked before the missing external result. That design fails the decisive pre-adoption cut. A static root paired with an outside static actor supports the handoff, but its root publication lacks an ordinary invocation-outcome delivery to that actor. These are construction limits for the prior grammar, not an impossibility for arbitrary protocols.

## One bounded extension

The construction adds one optional `InvocationHandoff` to a separately versioned `alan/identity-handoff-template/v1` descriptor. The original single-port constructor, template version and hashes remain valid. The new constructor admits exactly one second port on the entry member to its caller, with a different obligation from the captured reply. Both directions have exactly one `target` string (at most 1,024 bytes). The deployment binds the exact caller subject and generation, an invocation emission sequence, entry member via the chosen template, and both declared port names. There can be only one such template per deployment. The ordinary caller uses a reserved symbolic peer name and a matching declaration. A static subject cannot alias that name in the opted-in deployment. The binder derives the one dynamic member from Store namespace, original invocation operation and member name. Only admission of that exact invocation installs the two message permissions. An arbitrary target string, an unrelated invocation of the same template or a different obligation supplies no authority. A handoff does not grant endpoint access or adoption permission.

The extra messages use existing ordinary Send, Receive, first authorization, exact permission, typed admission and consumption transitions. The bound issuance reply remains separate. This additional deployment is outside the earlier Series 1 closed-template fragment. Its envelope has one parent resource root with one invocation, one created source, one original mutation debit, depth one and transport capacity one. A separate resolver resource root has capacity one and at most two lookup debits. No third semantic debit pays for the ordinary messages. Replaying the new profile reconstructs the scoped permissions and bound operands. The public data-bearing programs never receive the Store namespace, a host-supplied target, an endpoint inspection or a host Q acknowledgment. ## Actual pre-query cut

1. Static `parent/1` invokes the issuer at sequence 1. Dynamic `source/1` consumes that bound invocation request, commits its original request at sequence 2 and sends its truthful issuance reply `{issued:true,target:original}`.
2. Source sends the real ID to parent on the distinct ordinary port. Parent selects it and sends it to the separately rooted ordinary `resolver/1`. Resolver selects the ID and returns it. Parent consumes and checks the echo, then sends its own ordinary ACK to the exact source. Parent remains open at AwaitInvocation.
3. Source consumes the ACK on its ordinary handoff port and commits successful End. Its frozen invocation captures one admitted bound issuance reply, the single original effect, and no descendant invocation. Preparation reports exactly `external_outcome`. Parent has no selected invocation outcome. Resolver has a target and no world evidence. Source Q succeeds. Exact parent and resolver Q both return the open-authority error.
4. In the concrete cold control the registered adapter returned `unknown` with no network I/O. Both normal and race executions replayed the retained Store, reopened it and rechecked original Q. These are local construction results. Separate process experiments must establish application, observation, adoption, settlement, publication and selection in the controlled world.

The first service input to the resolver contains no fields and only releases the scheduled read. A distinct `refresh` input plays the same role for logical query 2. The resolver waits for its own query observation and reports the target, receipt fields and adoption disposition to the parent as ordinary application data. The positive parent first selects the original invocation outcome, separately selects that report, and checks target, receipt mutation/total, issued marker and adopted flag before taking the applied branch. The declared positive uses one unit original on a fresh zero counter. An alternate issuer waits for and selects a real unsuccessful result, records its defaulted fields and commits Failure; its parent can subsequently distinguish historical interaction failure from later evidence of application. None of these final branches were exercised by the pre-query cold control.
