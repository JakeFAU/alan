# Ordinary parent, result evidence, and useful continuation

Question: can an ordinary invocation parent carry a useful effectful child result, distinguish local failure from remote nonexecution, and continue while another original operation is unresolved? The following are tested properties of the declared authored programs and source-level limits of their public observations, not an arbitrary-parent impossibility theorem.

## Public program and transport

`examples/effectboundary/deployment.go` compiles an ordinary child with `Effect`, `Request`, guarded `Await`, and a caller response. Its parent uses `Invoke` and `AwaitInvocation` on the original invocation handle. The output is `{mutation,total}`. On `valid=false`, the child fails without a caller response. The parent explicitly records `local_failure_world_unresolved` and succeeds its own bounded reporting task; this status does not certify business success. Before selection, its own conservative state is `may_have_applied`, derived solely from its issued request and known child program.

The independent fixed peer has its own original operation, delta two, no child input or outcome dependency, and twelve finite private `Set` commits before its request. It is enabled from the initial provision. This bounded private prefix makes the primary delta-one operation eligible first without a host/oracle enable signal. Both use the same adapter registry and `MaxInFlight:1`. The raw observed request order is delta one then delta two; both mutations complete in every noncrash table row below, including the primary unknown path. The runner's slot accounting releases a completed unknown adapter before dispatching another adapter at physical capacity one. The probe establishes this one useful-progress sample; it does not establish general peer scheduling equivalence or fairness.

`adapter.go` is trusted deployment code using only public effects/schema interfaces. `Prepare` validates literal-loopback configuration and serializes `{Key,Profile,Delta}` without I/O. The key is the exact retained `Prepared.Request.Key`; executor-private authorization/epoch fields are not fabricated. `Execute` performs the real HTTP POST, validates the correlated fixture receipt, and returns the genuine raw response or transport error bytes. Every retained preparation is compared against the actual sent request bytes. The purity test proves zero endpoint contacts during preparation in this probe and then observes a real Execute contact; source inspection supplies the no-I/O argument for all accepted inputs.

The separate module `examples/effectboundary/consumer` imports only public ALAN packages. It supports init, run/recover, inspect, and replay. Host reports and inspections are printed for researchers and are never selected by the authored parent. No parent code reads endpoint state, private SQL, host reports, fixture counters, or a hidden reconciliation channel.

## Actual observations

The normal evidence is `evidence/parent/normal/`; final race evidence is `evidence/parent/race-final/`. Each compressed JSON contains exact retained inspection rows, original request keys/wires, endpoint-side request/receipt samples, root and peer projections, Run/recovery reports, and replay. These in-process HTTP probes are distinct from the independent persistent endpoint/SIGKILL process witnesses.

| Case | Endpoint primary application | Retained primary result | Ordinary parent selected fields | Parent continuation |
|---|---|---|---|---|
| Completed | One | `validated`, actual receipt | `succeeded/member_succeeded`, response present, exact mutation/total | PC 6 succeeded; `historical_application_receipt` |
| Selected unsuccessful | One, genuine receipt returned | `selected_error`, raw valid receipt preserved; normalized integer zeros | `failed/member_failed`, response absent | PC 9 succeeded; `local_failure_world_unresolved` |
| Real postcommit connection loss | One, connection closed after application before response | `transport_error`, actual Client.Do EOF/error text, HTTP status zero; normalized integer zeros | `failed/member_failed`, response absent | Same selected fields and conservative continuation as selected unsuccessful |
| Candidate unknown | One, genuine receipt acquired transiently | No result row; one unresolved allowed adapter attempt | No `child_status` or response fields selected | PC 2 open at original `AwaitInvocation`; `may_have_applied` |

The second and third cases have different host knowledge. In the selected-error case, an inspector can parse the retained raw receipt and, under the honest fixture's receipt-after-commit contract and binding checks, establish historical application. Its normalized `valid=false` does not erase those raw bytes. In the actual connection-loss case, only the transport failure is retained locally; the independent endpoint oracle establishes application. Neither failed child envelope communicates a nonexecution fact to this parent. The `unknown` case intentionally loses a genuine volatile receipt by returning disposition unknown; it is neither a transport error nor process death.

Reopening each in-process case with a success registry causes zero new endpoint contacts. Unknown adapter attempts remain unresolved; changing the registry does not authorize a repeat. Replay adds zero endpoint contacts and checks retained consistency, not an independent proof of compiler semantics.

## A failed child can be selected before any adapter result

`TestParentSelectsPrivateFailureBeforeEffectResult` uses a separate child whose real control flow is Receive, Request, private Failure. An allowed reserved worker is held at adapter Execute entry before its delegate can POST. While held, the child fails and the parent selects `failed/member_failed`, response absent, then succeeds its reporting continuation. At that coherent inspection there is one adapter attempt, zero adapter results, and zero endpoint contacts/applications. This selection is not a first-permission suppression: the retained attempt is allowed. Releasing the worker produces a real mutation and authentic late result while the failed child and completed parent stay closed. Before and after retained rows are archived. Snapshot/inspection observes this schedule; it supplies no ordinary observation and changes no authority.

This directly falsifies the inference “a selectable failed invocation outcome proves the child's external effects did not happen.” In fact the failure can be published while the allowed effect is still outstanding. The retained late evidence does not reopen child control. This probe has no process crash; its causal gate holds a real worker after reservation.

## Actual process-loss boundaries

`internal/durabletest/phase2_crash_test.go` adds `TestPhase2ParentAdapterCrash` through the adapter-enabled executor subprocess and independent persistent resource. Its process-normal/process-race evidence files are named `TestPhase2ParentAdapterCrash_unknown-parent-crash.json` and `TestPhase2ParentAdapterCrash_recorded-parent-crash.json`.

The unknown-parent-crash case SIGKILLs after acknowledged durable adapter reservation and before Execute. A genuinely fresh executor retains the ordinary root's original await: open, `may_have_applied`, no selected child status, one attempt and zero results. There is no world application or invented receipt. The recorded-parent-crash case SIGKILLs after genuine durable result recording but before settlement. A fresh executor settles the original result, the child sends its legitimate response, and the parent succeeds with `historical_application_receipt`; recovery makes no additional endpoint contact. PID/signal/exit, executable identities, original and recovered retained stores, endpoint ledger and acknowledged barriers belong to the process worker's raw evidence. No peer is included in these crash cases; peer progress is established separately above.

## P0, P1, and P2 disposition

P0 awareness is supported for this program: its own original issued request and known child program justify “may have applied” even with no selected result. A dedicated unknown event is not necessary for this conservative awareness. It does not establish a launch or application.

P1 precision is limited by the selected information. The ordinary failed invocation envelope conveys member failure and absence of a reply; it does not convey the child's adapter disposition or authorization reason. The private-failure schedule proves this envelope can coexist with an unresolved allowed effect. The actual connection-loss witness proves it can coexist with an already applied effect. The separate allowance test retains effect_limit with no worker or world mutation. Such a denial is normalized to valid=false and would take the same guarded no-reply failure branch as transport_error in this authored child. This comparison across admissible budgets follows the public program and normalization rules; the allowance test itself used a static member. The selected parent envelope cannot distinguish these cases. Successful receipt forwarding gives the finer historical-application fact under the declared trusted endpoint contract; it says nothing about a subsequently mutated resource's current total.

This is not a claim that all typed encodings are inadequate. An application could forward a genuine `source_denied`/`grant_denied` result with its precise trusted-dispatch meaning, forward a transport disposition or receipt, or distinguish private failure in its response schema. A label invented without the corresponding evidence would establish nothing. Forwarding more information can improve parent precision but supplies neither a missing receipt nor a new same-operation reconciliation capability.

P2 action is conditional. The success and failed-envelope paths execute ordinary reporting continuations; the unknown-result/crash path remains at the original await because the child has no selectable result and adapters conservatively do not re-Execute an allowed missing-result attempt. The parent has no raw adapter-result injection, read-only endpoint query, or public adapter same-key resubmission operation in this program/interface. It could issue a new invocation, but that creates another operation/key and is a new business attempt, not recovery of the unresolved original. A declared new endpoint reconciliation effect, a child response carrying actual evidence, or an explicit retry policy with matching authority are concrete follow-on choices; this campaign adopts none of them.

## Verification and scope

Executed with Go 1.27.3, CGO, readonly cached modules: normal and race tests of `./examples/effectboundary` with integration tag; normal and race tests of the separate consumer; focused vet of both; separate-consumer module verification and build. Exact commands, environments, executable/source hashes and outputs are in `evidence/commands/parent-*` and `consumer-*`. Final peer refinement is covered by `parent-normal`, `parent-race-final`, `consumer-normal-final`, and `consumer-race-final`. Earlier initial evidence had the peer contact first; it is retained under `parent/initial-normal`, `parent/race`, and initial command records and is not credited with continued post-primary transport work. The source-only and parent/child artifacts did not change in this refinement; only Peer=true provisions gained the finite private prefix. Process tests are separately recorded by their owner.

No production behavior, uncertainty policy, retry policy, cancellation rule, or endpoint reconciliation capability is introduced here. The ordinary parent distinguishes business evidence from its own reporting completion; the host/oracle distinction remains explicit. The result is a tested useful effectful composition with a precise unresolved boundary, not closure of Pillar V or a theorem about arbitrary recovery contexts.
