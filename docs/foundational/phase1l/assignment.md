2. Build one parent with two invoked children
Introduce a new context C_inv, using existing public authoring operations:
1. Invoke the candidate A or B with the K1 request; retain its original handle.
2. Independently invoke the original S with the original request's id/value; retain its original handle.
3. Await both original invocation outcomes.
4. Decide the parent result from those actual outcomes.
Both invocation intents must be durably committed before the parent's first await or terminal decision; their admissions/executions may interleave. Check the actual compiled order and retained history. Do not wait for the candidate before starting S. No separately provisioned reporting peer, forwarding worker, report/ACK channel, or raw-artifact workaround is needed.

Keep A/B/S source and retained artifact identities unchanged where the inspected interfaces permit. Reuse existing independently authored candidates; do not commission new implementations or rewrite them to fit the experiment.

Use one context definition/builder parameterized by the candidate template. No candidate-specific branching, different limits, or different result checks. Compiled links/catalogues and artifact identities can differ when the binding changes; do not claim byte-identical parent artifacts. Record exactly what differs.

Preserve strict outcome handling:
- Parent success requires both actual successful, present, correctly correlated results: candidate id equals the request id and value equals 1 - value; S preserves the id and returns its existing value zero.
- Retain known failures/refusals/absence. Consume the other required outcome before the parent's normal final decision.
- A pending required outcome keeps the parent pending; a finished sibling does not discharge it.
- Authorized cancellation remains outside the positive completion profile.
Guard response-field reads with status/presence checks; absent outcome bindings must not become invented zero-valued responses. Observe the parent's retained result/state and root/aggregate publication through existing public inspection. This observation boundary must not introduce a new ordinary-message delivery obligation at root termination.

The harness may inspect or drive legitimate public transitions. It must not compute replacement results, manufacture observations, change retained projections, or make the parent's decisions.

4. State the guarantee before qualification
Investigate this bounded implication:
A refines K1, B refines K1, and C_inv[K1] satisfies G
    => C_inv[A] satisfies G and C_inv[B] satisfies G.
Define G concretely: correct required application results, completion of both required invocations and the parent under the stated progress assumptions, actual consumption of the original outcomes, and resource compliance.

The reference premise matters. Establish C_inv[K1]'s guarantee before claiming that substitution preserves it. If the reference fails, that is a context failure, not yet a substitution counterexample.

Use the original tiny positive domain:
- id in {1,2}, value in {0,1}, candidate mode answer.
- Invocation and dynamic-created-run limits I=R3.
- Depth cap 2; effect allowance zero. This gives four payload configurations per product; redundant depth slack is not another required census.
- One fixed parent run; stable grants/generations, no external cancellation, and explicit eventual service.
Expected successful accounting:
Binding	Dynamic invocations/created runs	Fixed runs	Effects
A + S	2	1	0
B + helper + S	3	1	0


Verify these counts. Depth is not an additive ticket: candidate/S are direct children and B's helper adds one nesting level. Both candidates receive the same worst-case allowance. Use the existing single-host profile and physical capacity one for initial concrete checks; physical concurrency is distinct from cumulative I/R charges. Their different permitted charges remain observable; this is not exact-debit equivalence.

Admissibility is defined constructively by the invocation tree, original-handle joins, resource envelope, and environmental assumptions. It must not mean “the executions that passed.”

6. Minimal controls and one recovery witness
Keep qualification proportional to this question:
- Contract violation: reuse a genuine executable K1 mutant, such as wrong id. Preserve its actual consumed reply. The independent checker must reject the conformance/success claim for that violation while recognizing the honest failed execution as a valid history. Merely seeing the parent fail does not replace checking candidate conformance.
- Insufficient allowance: use B with I=R2. Preserve whichever actual admission is refused and its charges; do not prescribe which competing operation must lose. This case lacks the positive K1 worst-case entitlement and is not a counterexample to the sufficient-budget substitution claim.
- Outcome policy: use focused existing fail/absent and pending modes to verify that the new parent does not silently skip the second join, promote absence into success, or invent a terminal outcome for pending work. No full cross-product is required.
- Recovery: with B, reach a state where both original invocation intents are committed, the parent has consumed exactly one original outcome, and the other is required but unconsumed. Prefer unfinished child work if existing facilities expose it; otherwise label a retained-but-unconsumed outcome precisely. Acknowledge the checkpoint, send real SIGKILL, and reopen the same database in a fresh process. Preserve handles, artifacts, logical identities, consumed evidence, and spending; verify actual completion without duplicate consumption. Record the exact predicate/profile; a checkpoint name alone is insufficient.
Use public execution for the program. Existing test-only observation facilities may establish cuts, with no reentrant store calls under held boundary locks. No redeployment, resubmission, replacement handles, or reconstructed work on recovery.

Check raw selected observations before normalization. Read both original handles from authentic retained state and link them to their committed intents, admissions, outcome observations, and selection history; never construct operation IDs from an expected sequence tuple. Publication or final register values cannot substitute for what the parent consumed. Add only focused evidence checks needed by the new mapping; reuse existing decoder safeguards.
