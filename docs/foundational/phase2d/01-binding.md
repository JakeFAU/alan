# Two fixed identity handoffs

## Construction question and obstruction

Can one static caller receive the genuine operation identities of two invoked issuers, acknowledge them independently, and leave both original invocations waiting for their own external result? At integration base `2612a85b287d95aa95f11e35c57b8b7b8dc26c6d`, the public test compiled two children. Each used an ordinary Request, sent that Request's retained ID, waited for its echo, then issued its public reply and ended. The parent compiled and provisioned two v1 templates, distinct caller ports and obligations, then invoked both before its first receive. Store creation returned `ambiguous caller handoff peer`. The existing implementation checked for exactly one symbolic port and returned after binding one template. No actor ran on this rejected deployment. The archived baseline test decompresses to SHA-256 `e10e0b1ec3622d82fe1a503e9952d1c3a53df20237a20909915862fd99c931ec`, the test input named in the command manifest. ## Narrow profile

`author.NewPairedHandoffTemplate` constructs one `alan/identity-handoff-template/v2` descriptor. Both descriptors use the ordinary `InvocationHandoff` locator and the existing reserved caller-side symbolic peer. The deployment requires exactly two v2 descriptors for the same actual static caller, at generation and initial authority revision one. The owning caller resource root permits both. Distinct positive emission sequences identify two ordinal-zero invocations. Distinct caller port names and identity obligations identify the instructions to rewrite. Child port names can coincide across the two child programs. On each child the handoff port belongs to the designated entry member, uses the ordinary caller peer, and differs from the captured invocation-reply port and obligation. Each handoff direction declares the exact closed record `{target: string[1024]}`. The two templates cannot occur as nested dependencies. The rest of the deployment may contain closed pure templates.

The descriptor version participates in the template's content address. This boundary changes no Store table or key format. A new template requires the new public constructor or an equivalently validated explicit descriptor. The v1 constructor retains its singleton limit and byte interpretation. Original closed templates keep their existing version and constructor. The test suite separately opens the previously archived v1 original-effect Store and observes its previously selected applied decision. No migration installs new authority in an existing Store.

## Source gates and evidence

* `author/invocations.go` selects the version. `composition_binding.go` validates the template shape before retaining its ID and again while binding the invocation. `invocation_handoff.go` validates the pair, its actual caller, allowed root, endpoint schemas, obligations, and static alias/grant exclusions. It materializes each peer from Store namespace, the locator's invocation operation and the exact entry member.
* At caller binding all matching templates are processed in deterministic ID order. A message instruction must match the placeholder and its distinct obligation. Its literal peer and corresponding retained port are rebound together. Communication uses the existing ordinary message authorization, delivery and selection. The handoff string gains no dispatch, read or import authority.
* Only admission of the matching actual template at the specified caller operation grants the two directed message permissions. An accepted invocation at another slot may create legitimate ordinary members while granting no such channel. The direct control commits both Invoke intents, inspects zero channel permissions, then checks the exact subject, peer, operation, revision, and obligation of each permission after each individual admission. Swapping the locators between issuers with the same entry member name yields zero handoff grants after both admissions. Offline replay rejects a relabeled genuine grant on a disposable Store. Existing composition replay derives the permitted rows from deployment and actual admissions.
* In the construction positive the parent selected both distinct Request IDs, each child selected its own matching echo and terminated, and each frozen invocation contained precisely its original missing external effect. The local fixture adapter returned unknown without contacting an endpoint. This tests target discovery and selection independently of world evidence. The separate phase construction and process histories must establish resolver roots, real applications, adoption and the full product.

The first v2 compile retained an unused import; the failed build and correction remain in the records. The final construction selectors passed with Go 1.27.3, CGO enabled, offline readonly modules, normally and with race instrumentation. They include the historical v1 Store and closed-template controls. These are construction-gate runs on their recorded source inputs, separate from the phase-wide frozen-source campaigns.
