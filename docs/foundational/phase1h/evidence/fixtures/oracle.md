## Oracle scope and identities

Initial round is numbered 1. The semantic labels alpha, beta, gamma and slash descendants express lineage only; wire ID representation is frozen separately in the JSON. A work ID is distinct from the invocation operation, invocation scope, member run, public result, effect intent and external reservation identities. Those runtime identity bytes are unknown before execution. The oracle requires an injective work-ID-to-committed-operation mapping, unchanged on fresh-process recovery, and original result identity correspondence. It must not compare runtime IDs against invented fixture constants or assume identical IDs across separate stores. Compare semantic work/round/order between direct and nested runs, while each store has its own authenticated runtime identities.

All leaf invocations are children of the same adaptive scope. A causal predecessor in this ledger is a work/result dependency, not the runtime invocation parent. Descendants do not add invocation depth. Within each round, stable order is parent-frontier order and then left before right. A round barrier requires all required outcomes to be known and their exact ordered evidence retained or deterministically reconstructible before any next-round leaf admission. No work is admitted from response absence.

## Accounting established independently

One statically provisioned resource root is fixed cost, reported separately, and never charges invocation admissions or created runs. The adaptive invocation contributes one admission and one run. An ordinary nested wrapper contributes another admission and one run. For n accepted one-program leaves, direct admissions/runs are n+1/n+1 and nested n+2/n+2. For n accepted unchanged two-program evidence leaves, admissions stay n+1 or n+2 while created runs are 2n+1 or 2n+2. Both helper members occupy the leaf depth; no extra invocation is charged for its ordinary internal messaging.

Direct deepest path is root(depth0) -> adaptive(depth1) -> leaf members(depth2). Nested is root0 -> wrapper1 -> adaptive2 -> leaf members3. Empty input reaches adaptive depth1 direct or2 nested and still incurs its enclosing calls. Additional rounds never change these depths. A separately invoked round coordinator is outside these formulas and must be rejected or explicitly re-reviewed before implementation.

With eight accepted leaves the maxima are 9 direct /10 nested admissions, 9/10 single-program created runs, or17/18 evidence-helper created runs. The unchanged helper configured for two model and one lookup requests uses at most three external reservations per leaf (24 for eight), since repeated reservation delivery charges once. A clarification-only fixture spends exactly one model reservation per leaf; an answer fixture spends exactly two model plus one lookup. Pure controlled leaves spend zero. An unknown allowed reservation remains spent; a denial spends zero. Root limits remain32/64/96 across every round and restart. Limits are ceilings, not spending authorization.

Physical capacities1 and2 change allowed transport overlap, not logical frontiers, ordered results, invocation/run charges or maximum depth. More logical work than slots must progress through ordinary admissions while parents wait without holding physical slots. At capacity2 require an acknowledged later result while an earlier transport remains held; at capacity1 require independent pure/admission progress while a transport is held. Watchdog duration is not causal evidence.

## Independent comparisons and authentic negative

The positive comparison consumes the literal JSON expected frontiers and returned observations. It must compare accepted work IDs, exact input payloads, output values, stable round/result order, causal predecessor, stopping reason, remaining frontier, and charges. It must never call the adaptive builder or its derivation function. Runtime/replay protocol validation is separate.

A faulty ordinary application must consume actual returned gamma=0 in the paired case yet substitute the primary predetermined follow-up frontier containing gamma descendants. It must reach that leaf invocation/admission boundary with authentic runtime intents and otherwise valid public schemas. The unchanged paired-case oracle rejects extra gamma descendants, wrong count and charges. If runtime success and replay both accept that authentic but semantically wrong program, report application semantic rejection explicitly; do not call it a runtime protocol rejection. Merely editing monitor input, corrupting a store, or failing at an unrelated schema check does not establish this negative control.

## Identity, failure and recovery checks

Reject duplicate work IDs in seeds before any seed leaf work. Reject duplicates within a derived frontier or against any previously admitted frontier before admitting any item of that invalid frontier. Equal payloads under distinct IDs must retain distinct operations/results and both charges. Compare IDs rather than treating observation/payload equality as deduplication.

Known non-success leaf outcomes are inspected before reading any optional payload. A missing response remains absent. A failed helper may retain diagnostic `invalid_result` with failure status; that diagnostic is not success. A root-budget denial after application acceptance is a retained known negative result, not refusal of the original application request. Denied leaf attempts add no admissions/runs; prior accepted work and charges persist. Unknown required external work remains pending/spent under the original operation. No next-round decision or public success may treat it as observation0, failure, or permission for replacement work.

At decision-before-admission, partial-next-frontier-intent/admission, and partial-next-round-consumption cuts: acknowledge retained events, SIGKILL the actual subprocess, reopen in a different process, and compare exact original accepted inputs, committed decisions/evidence, pending operation identities, original consumed results and resource counters. A decision may be reconstructed only from retained exact inputs/outcomes without repeating completed external work. Recovery cannot reset bounds, allocate another root, resend input, or charge an existing operation twice.

Root closure between decision and admission must fence every not-yet-admitted descendant. Already admitted work/results and spent unknown attempts remain as historical evidence; late evidence cannot reopen a closed parent or be rebound to newer work. Read-only replay runs without credentials/adapter registry and with the existing supported OS network denial; durable store/ledger hashes and provider contacts stay unchanged. Retain actual interrupted PID and acknowledgment identities, not just a timeout result.

## Final frozen stopping precedence

After all required current-round outcomes are known, use the first non-success in frontier order: a rejected outcome with invocation_limit/created_run_limit gives root_budget_denied; every other non-success gives leaf_non_success. Retain successful siblings' derived candidates without admitting them. Next check invalid/missing successful observations, then candidate duplicates within the frontier or against all admitted history. Only then check empty (exhausted/complete), total-work overflow, and round bound, in that order. The whole next frontier is either accepted or preserved; no prefix admission on application bound. Thus work_limit wins over round_limit when both bind, and exhaustion still succeeds at a fully used bound. Duplicate validation wins over limits, including the sixteen-candidate collision fixture.

Orderly work_limit/round_limit return protocol success with application complete=false and the exact unperformed frontier. Hard failures send their stopping result then fail. Runtime denials happen after application frontier acceptance: application work_count includes denied items, while root admissions/runs charge only accepted invocations. The literal budget fixture accepts all three initial app items, permits only alpha and beta at the runtime layer, rejects gamma with its original operation, retains beta's candidate id7/value0, and stops root_budget_denied. Direct max invocations3 (or scalar created runs3), nested4, produces accepted-only charges3/4 and two scalar reservations. Failure/invalid-observation fixtures retain successful gamma's two candidate children but admit neither.

A required unknown beta with all three scalar transports already contacted has three spent reservations, no next-round decision, no public application response, and no replay/recovery repeat contact. Its eventual outcome is unresolved; a pending observation is never rewritten to0 or knownfailure.
