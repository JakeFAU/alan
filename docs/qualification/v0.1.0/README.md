# ALAN v0.1.0 public runtime qualification

Candidate `bea0acc86d9a7302ccc3511327455922503c4a57` was evaluated against public main `64a692b6f82ae10353f50c8741377166bc6cf854` on November 24, 2026. The release target is a Go developer building a bounded, single-host agent backed by local SQLite. The [candidate manifest](candidate-consumer.json) pins the Git commit, Go module and archive. This evidence lives outside the distributed module so it can identify the exact candidate it qualifies.

## Independent application

An empty application module installed `github.com/JakeFAU/alan/runtime@v0.1.0` from an isolated file proxy. Its private module and build caches started empty. Workspace mode was off, and the application had no replacements or imports from ALAN internals. The candidate producer verified Go's VCS origin against the candidate commit and checked both SQLite dependency sums against the candidate's go.sum. These checks used Git and the selected hashes as the local trust roots. The published check uses the public Go proxy and checksum database.

The packaged README supplied the commands. The editable Go application shipped alongside it in the module ZIP. Four separate processes admitted a ticket, suspended with zero paid attempts, resumed with the application's routing desk, inspected the expedited queue, and replayed five commits and one intent. The executable checked those facts and the single dispatch before printing its output. Public documentation lookups and `go mod verify` passed. The [Linux consumer manifest](linux-consumer.json) from [GitHub Actions](https://github.com/JakeFAU/alan/actions/runs/45413385214) records the same four outputs, both module sums and the identical ZIP SHA-256. This second host used Go 1.27.3 on Linux/amd64 with CGO. See the [quickstart](../../../README.md#build-your-own-durable-agent) and [reproduction procedure](../../releases/consumer.md).

## API and persisted history

Store, Provision, ExecutionSnapshot, RunOptions, Limits, Input, RunReport and RunProgress are now runtime-owned public types. The store retains all 24 previously exported owner methods. Use keyed configuration literals, including when adding AssetScopes. The package split remains `author` for definition, `schema` for data contracts, `effects` for trusted adapters and `runtime` for execution and ownership. Hosts obtain a store through `Create` or `Open`, call `Close` to release ownership, and pass positive step and dispatch budgets to each run. Distinct public outcomes include unavailable capability, invalid adapter output, ineligible continuation, closed target and denied lifecycle source. A malformed input can match `fs.ErrInvalid`. Known schema refusals use their existing admission or result disposition. OS, SQLite and context failures preserve their underlying errors where supplied. Some secondary retained-record types remain aliases. The public accessors and [inspection guide](../../inspection.md) describe their use. The existing generic effects.Copy helper assumes a validated, JSON-round-trippable value. The runtime checks untrusted live result serialization at the adapter boundary.

New stores with assets or explicit bindings use formats 17–30, corresponding to original profiles 3–16. The new formats retain a capability-to-ID/version manifest, independently bind it to the metadata, and verify each recorded request against that contract. Existing stores keep their original whole-corpus interpretation. The host must give a capability an explicit list when an existing corpus adapter is provisioned in a new store. No adapter registration or mutable source is required to replay.

The candidate inspected, replayed and opened a disposable copy of each original format 3–16. Ten inputs were verified against the historical archive and its member manifest. Four came from the base writer's public authority histories and conflict promotions. The [input hashes](historical-inputs.json) identify this run's exact copies. The [four stopped authority inputs](historical-authority-inputs.tar.gz) preserve the generated namespaces used here. Fresh runs of the pre-release writer choose new namespaces. Old and new copies are finite examples of each profile. The candidate verified all 14 corresponding scoped formats, and the frozen pre-release CLI rejected all 14 through inspect and replay. The [compatibility policy](../../releases/compatibility.md) covers API support, backup, promotions and upgrade limits. There is no automatic scope conversion or general downgrade.

## Performance and limits

The 256-operation series compared the pre-release and candidate binaries in four balanced blocks after four excluded warm-ups. Every one of the 20 runs checked 256 contacts, spent attempts and replayed intents, 255 continuation approvals, and 1,023 reductions and history rows. Each reopened and replayed its store. Timings are medians on one shared M4. The source, orders, individual durations and before/after host load are retained. [Benchmark procedure](benchmarks/README.md) · [Source and binary hashes](benchmarks/bounded-256-build.json) · [Samples](benchmarks/bounded-256-rows.jsonl) · [Medians and ranges](benchmarks/bounded-256-summary.json)

| 256 operations | Pre-release | Candidate | Median paired change |
| --- | ---: | ---: | ---: |
| Full Run window | 4.752 s | 4.704 s | −0.93% |
| RunProgress window | 1.335 s | 1.334 s | −0.10% |
| Full Run lifecycle | 6.618 s | 6.565 s | −0.80% |
| RunProgress lifecycle | 3.189 s | 3.192 s | +0.13% |

Initial store creation cost more. In the series, creation increased by 6–8 ms (2.4–2.6% paired). In the isolated one-step Create/Close benchmark, the median rose from 2.08 to 7.63 ms with no assets and from 3.15 to 7.53 ms with a 128 KiB asset. The increase occurs once per new store and buys validation before the path is reserved and durable publication of the initial image. Across the nine measured InspectExecution, Open and Replay cases, the candidate medians were within 4% of the base. These observations cover the measured sizes, cases and host. [Paired creation and recovery measurements](benchmarks/creation-recovery.json)

Store creation latency and peak memory for larger provisions warrant continued measurement. The observed one-time increase does not block this release for bounded agents that reopen an existing store. The bounded-series workload and recovery results preserve the relevant computational checks.

Local verification used Go 1.27.4, CGO enabled, Apple clang 21.0.0, Darwin 27.3.0/arm64 on an Apple M4, and the pinned go-sqlite3 v1.14.52 with SQLite 3.53.4. The filesystem supported WAL, durable sync and exclusive ownership. Creation temporarily holds the initial database image in memory. Failure injection killed processes on this filesystem. The separate Linux run qualified the packaged consumer. Physical power loss and other filesystem configurations were outside the local fault-injection matrix. Archived research timings and claims retain their original revisions and workloads.

The authorized-publication step is to tag the exact candidate commit, then run the published-mode command with the retained manifest. That run must match the public tag's commit and both Go module sums and pass the same application checks. The candidate procedure created its tag only inside a disposable local packaging repository.
