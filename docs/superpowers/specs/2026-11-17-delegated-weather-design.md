# Delegated Weather: a bounded retained-helper replacement

Date: 2026-11-17. Status: design for the approved implementation direction; no implementation or qualification result is asserted here.

## Question and bounded claim

Can the fixed Outing caller complete the same frozen planning question when Weather delegates all forecast work to one ordinary retained helper, while retaining the original forecast obligations across a process interruption?

Build a third Weather variant, `delegated`, alongside `assess-first` and the deliberately incompatible `confirm-first`. Keep Outing's definition, compiled artifact, initial inputs, public proposal/assessment/decision schemas, candidate ordering, and selection policy identical. Demonstrate successful replacement under an explicitly sufficient envelope; expose its extra invocation and created-run costs. Preserve a separately reported helper-admission refusal and the existing circular-dependency obstruction. Establish independently checked finite model results and observed model/runtime correspondence for specified fixtures and cuts, not universal runtime refinement or general ALAN congruence.

The initial delegated feature accepts **zero through two locally eligible candidates**. Existing direct variants retain their current four-park/four-slot bounds. The delegated start and replacement commands reject more than two eligible candidates before creating a Store or contacting the endpoint, with an explicit supported-domain error. Ineligible configuration rows remain bounded by the existing normalization rules. The model abstracts these already frozen rows away; calendar normalization is covered by the existing separate tests, not proved by the protocol model.

## Approach and settled choices

The user selected genuine delegation rather than extending the direct computation only. One helper per eligible candidate would introduce needless invocation multiplicity, admission races and a larger domain; do not implement that alternative. One helper per proposal gives a real retained computation boundary with the smallest protocol: one request and one response containing the whole ordered assessment list. Invoke it even for an empty list, so the declared cost and admission-refusal behavior are consistent and inspectable.

Use a source-only Python checker with the standard library, including `sqlite3`, for an independent finite protocol model and evidence reconstruction. Keep protocol rules in `check.py` and the raw reader/correspondence rules in `evidence.py`. The launcher captures and hashes both source buffers before executing either in fresh namespaces, then connects their API explicitly; no local import or reused module cache may become an unrecorded execution dependency. This separation keeps the complete raw reader independently reviewable without expanding the runtime. The Go application remains usable without Python; Python is required for the independent qualification command, not ordinary start/resume/report use. These are implementation choices, not claimed historical user wording.

## Program and wire contracts

### Existing public boundary

Outing continues to send `proposal {proposal_id, candidates}`, receive `assessment {proposal_id, assessments}`, then send `decision {proposal_id, candidates, outcome, selection}`. Its byte-identical `outingDefinition()` remains the source. Existing ordered exact candidate coverage and nonempty unique `forecast_operation` checks stay in place. No helper identity is added to that public payload. Every assessment's forecast handle remains the **original adapter operation**, now owned by the admitted helper run.

The existing documented policy is the model's application contract: normalized candidate order is one-way travel minutes, UTC start, then park ID. A known valid forecast is suitable only when the retained allowed-code set includes the codes at both requested hours. The selected option is the first suitable candidate in that order, even if another candidate is unavailable. With no suitable candidate, any unavailable assessment yields `unavailable`; otherwise the result is `no_match`, including the empty list. Temperatures remain evidence and are not an additional selection threshold. The model's candidate indices refer to this frozen order.

Keep `weatherDefinition(assessFirst)` and `weatherDefinition(confirmFirst)` structurally unchanged. Do not add optional fields to the serialized `configuration` or modify old initial projections, schemas, metadata, artifact names, or existing composition roots. Capture pre-change artifact/configuration bytes as compatibility fixtures or assertions against the pinned base before implementation changes.

### Helper template

Add `weatherHelperTemplate() (author.Template, error)` and `delegatedWeatherDefinition(helper author.Template) author.Definition` in `delegated.go`. Use a single member named `worker`, an entry port `work`, a synthetic peer `caller`, and an obligation `assess`. The helper is an ordinary `author.Definition` compiled and retained through `author.NewTemplate(author.Application{"worker": ...}, "worker", "work")`.

The helper's duplex request is the closed record:

- `proposal_id`: existing `idField`;
- `candidates`: existing `candidateList`, with admission restricted to at most two eligible entries by the application;
- `units`: existing hourly units field;
- `allowed_weather_codes`: existing `weatherCodes`.

The response is exactly `assessmentSchema`. The helper receives this request, performs the current sequential `assessWeather()` behavior on every candidate, sends `{proposal_id, assessments}` once on `work`, and succeeds. Its success means that the assessment computation completed; a known invalid/unavailable forecast still produces an assessment with `weather_status=unavailable`. It does not mean an outing was possible. An admitted forecast with no durable result blocks the helper at its original await and prevents any completed reply. The helper owns the hourly adapter declaration and has no public Outing ports or nested invocations.

### Delegated Weather parent

The parent receives and validates the original proposal before any invocation. It calls `author.Invoke("helper_call", "assess", request, nil)` exactly once, then `author.AwaitInvocation("assess", "helper_call", bindings)` retaining status, reason, response-present and separately prefixed response fields.

The parent checks `response_present` before reading optional response fields. For a rejected invocation it fails without an assessment or decision; the report retains the refusal and Outing's waiting obligation. For a non-success helper outcome, missing response, wrong proposal identity, or malformed coverage it fails without manufacturing an assessment. Accept a response only when status is `succeeded`, response-present is true, proposal identity matches, and ordered candidate fields and original nonempty unique operation handles exactly cover the proposal. Copy the accepted assessment list, then send the unchanged public assessment. Receive and validate Outing's decision, recompute its unchanged selection policy, compare outcome and selection, and use the current `finishDecision()` behavior.

There is no direct forecast fallback, synthetic assessment, automatic retry, replacement original operation, parent success before the child's published outcome, or empty-list shortcut around invocation. The retained helper may succeed even when parent and Outing later fail with `unavailable`.

## Source authorization and the scheduling domain

A committed ordinary message is not yet deliverable. Owning source inspection (`internal/executor/messages.go`, `invocation.go`, `invocation_outcome.go`, and `runner.go`) requires the model to distinguish **commit, first source authorization, destination admission, dispatch acknowledgment, and receiver selection**. `AuthorizeIntent` records its first disposition durably. For an ordinary public message, first authorization after sender termination returns `source_closed`; delivery records `source_denied:source_closed` and creates no inbox observation. A later attempt, fresh owner or unchanged permission grant cannot replace that first refusal. Conversely, an allowed first authorization survives later source closure; admission still independently requires an open, current, unretired permitted receiver and valid payload. Acknowledgment may record a refused admission and proves neither admission nor consumption. Stable generations/revisions, fixed permissions, no retirement/cancellation, and no extra operator inputs remain explicit domain restrictions.

The fixed example's supported cuts use one transport identity per original message. Repeated calls with that identity remain idempotent. The ordinary runtime API also permits distinct transport identities for one logical message. This example and its independent checker exclude those cuts from the supported domain while accounting for every retained row. A manual recovery or paired authorization control must acknowledge the original transport before returning delivery to `Run`, or use the runner's deterministic transport identity and retain the same admission on resume.

The helper's bound reply has a different lifecycle. `compositionReplyBinding` recognizes only the original admitted template's entry member sending to its exact caller generation and entry obligation. That reply may obtain its first authorization after helper local termination: the current v1 source check exempts the authenticated bound reply from source-closed/retired checks, but not generation/revision mismatch. `recordCompositionReply` then records the authorized, schema-checked reply in invocation evidence instead of directly creating the ordinary public-message inbox observation. Invocation publication/delivery creates the parent's correlated outcome observation later. Do not apply this exception to Outing's decision, Weather's assessment, or the parent's invocation request. Invocation admission independently rechecks the caller/root scope is open; the fixed parent remains at its await until the helper outcome, and the fixed helper awaits each original effect before replying. No v2 parent-returns-early behavior is assumed.

The helper cannot silently publish an empty successful result merely because its committed reply has not yet been admitted. In v1, `freezeCompositionScope` and `captureCompositionIntents` capture the complete committed prefix inside the terminal transaction, including every authenticated bound reply intent independently of delivery order. `prepareCompositionScope` checks each captured reply and returns `Pending="reply_admission"` while its `composition_replies` record is absent; it does not substitute an absent response at this cut. After a genuine recorded reply, one accepted reply supplies `ResponsePresent=true` and its exact response. A successful member with no committed/accepted reply can instead produce `missing_reply`, and conflicting reply intents produce `conflicting_replies`; those are failed invocation outcomes, never acceptable completed assessments. The model and raw checker must preserve the frozen reply-intent set and this pending gate. Add a controlled helper-Send→helper-End→prepare-before-reply-admission cut, assert no ready/public outcome, then authorize/record that original bound reply and show the parent can consume only the later complete original outcome. This source-supported obligation needs concrete tests; no such test is claimed here.

**Broad-interleaving model, expected negative result.** Permit every declared local/service ordering, including delaying the first authorization of the final public decision while Outing executes its ordinary finite completion branch and End. A minimal n=0 known-input trace is: accepted/selected proposal; accepted/selected empty assessment; decision commit; Outing local Success; first decision authorization refused as `source_closed`; refused admission and acknowledgment; Weather remains open at its decision receive with no matching observation. The delegated version additionally performs its one accepted, completed helper invocation before the assessment. Outing local success, and potentially its own root publication, do not settle Weather's required receive. There is no successful completion suffix after the immutable refusal without changing this fixed application; initial completion can still be possible through another ordering. This is a **nonblocking counterexample**, not the `confirm-first` circular-dependency witness, a deadlock theorem for all schedulers, or a corruption case. Eventual service does not repair it. Preserve this legitimate raw trace and a paired allow-before-End / admit-after-End trace that can complete while Weather remains open. Do not weaken Outing's unchanged program or silently require committed messages to arrive.

**Positive constrained model.** Separately explore a named `preclose-authorization` subdomain: every ordinary public message whose sender can subsequently terminate must receive an allowed first source authorization before that termination; destination admission and receiver selection remain distinct transitions. In this fixed program, proposal and assessment senders cannot normally finish until downstream receives are satisfied. The extra decisive restriction is the Outing decision authorization before Outing End. Keep the authorization rule, immutable refusals and bound-helper-reply exception in both domains; a positive model cannot delete denial semantics. Report domain/premises alongside every `CanComplete` or nonblocking verdict. Positive nonblocking is a property to check only in this restricted domain with known completing fixture outcomes and adequate helper admission; the broad domain must retain the late-authorization witness even for those outcomes. This subdomain is an abstraction of an identified scheduling premise, not a complete model of `Store.Run` instruction-by-instruction or an unrestricted scheduler theorem.

**Why automatic runs can satisfy that narrow premise.** `Store.run` offers one pending internal delivery before its next local `Commit` each turn. `deliverOrdinary` performs ordinary source authorization, admission, then acknowledgment sequentially. Thus if a supported cut has Outing open just after its decision Send, Weather open waiting for that exact decision, the decision as the **sole pending internal delivery**, and no concurrent low-level mutations, a continuing automatic runner processes that delivery before any next local reduction can terminate Outing. If a bound/error/cancellation interrupts service before it completes, no later local commit in that interrupted service turn occurs; reopen resumes from the retained cut. An allowed authorization remains usable through a crash. This establishes only the local source-order implication under continued service, sufficient operational bounds and no Store error, not eventual completion after arbitrary cancellations or missing endpoint responses.

For the fixed fresh automatic execution, verify the sole-delivery premise instead of assuming it: earlier proposal/assessment messages are acknowledged before subsequent local selections; helper reply is recorded/acknowledged before normal helper termination; the invocation outcome is delivered before the parent's selection and public assessment; all original forecasts are settled/selected; no terminal observation routes, unrelated members or other pending internal messages exist. Root publications do not themselves add an ordinary public-message delivery. The capacity-one fixture does not establish the sole-delivery fact by itself. Inspect complete pending delivery records and original acknowledgments in the concrete decision-commit cut. Test the same premise after the declared supported recovery cuts. A hand-driven cut with an extra unacknowledged internal delivery or Outing already terminal without authorization is outside this automatic-runner justification and remains in the broad model, not silently admitted to the positive campaign.

Source authorization and destination admission are separate durable transactions, even though the automatic runner services them sequentially before a local commit. A crash can leave the authorization-only cut; a public low-level driver can also deliberately close the source between authorization and admission. The latter paired control exercises the broad model's preserved allow and must not be described as an ordinary automatic-runner schedule. Likewise the late-first-authorization counterexample is a public-runtime controlled schedule, not an observed failure of the default runner. Record both categories accurately. If application-specific `inspectPlanner` rejects the deliberately unsupported public-send schedule, retain `runtime.InspectExecution` plus the independent raw checker output; do not weaken the supported-deployment/report validator merely to present the negative control.
