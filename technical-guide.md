# ALAN Technical Guide: Retainable Interactive Computation

## 1. Why Agent Orchestration Breaks When Processes Die

Suppose an application runs an agent that queries a document corpus, asks a language model to draft an answer with supporting citations, and calls an external HTTP endpoint to record a decision or update a counter. Halfway through this workflow—after the HTTP request leaves the machine, or while a parent program waits for two child workers to finish—the operating system delivers `SIGKILL` (`kill -9`) to the process.

What survives?

In an ordinary agent orchestration framework (built in Python, TypeScript, or Go around an in-memory loop and tool callbacks), **the continuation of the agent lives in the call stack and heap of the running OS process**:
- Which step of the program comes next is encoded in the host language's instruction pointer and active stack frames.
- How much of the model or tool budget has been spent lives in local variables.
- Which child workers or external HTTP calls are in flight is tracked by live promises, goroutines, or open sockets.
- What permissions the agent holds are implicit in the closures and API clients passed down the call stack.

When that OS process dies, the residual computation vanishes. If a new process restarts the agent from the beginning, it either blindly re-executes external tool calls (risking duplicate mutations or extra charges) or halts without knowing whether the interrupted request ever reached the remote endpoint.

Even industrial **durable workflow engines** (such as Temporal or Azure Durable Functions) address process death by event-sourced replay of host-language functions rather than by making the computation itself a first-class mathematical object:
- Control remains an opaque host coroutine reconstructed by re-executing host code from step `0`.
- Supervision and retries are privileged runtime mechanisms rather than ordinary programs.
- External side effects are modeled as coarse two-state activities (`Started` → `Completed`/`Failed`), masking the intermediate failure windows between committing an intent, checking permissions, passing a local dispatch gate, mutating a remote endpoint, and recording a receipt.
- Identity is flattened to a workflow/run ID, and authority is coupled to parent-child creation.

**ALAN (Agentic Lambda Abstraction Network)** begins from a fundamentally different premise ([Monograph §1.1–1.2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L11-L38)):

> **ALAN is a programming-language semantics and crash-consistent execution engine that makes interactive computation a retainable, serializable value.**

In ALAN, declarative program definitions ([`author.Definition`](author/author.go#L18-L28)) compile ahead of time into immutable, version-bound instruction arrays ([`executor.Program`](internal/executor/program.go#L40-L44)). No host-language callback, closure, or Go stack frame is retained at runtime ([`author/author.go`](author/author.go#L1-L3)). At every step, the entire residual state of a running agent is an explicit, JSON-serializable projection ([`runtime.Projection`](internal/executor/program.go#L67-L72)) persisted in a single-host SQLite Write-Ahead Log (WAL) database ([`runtime.Store`](internal/executor/store.go#L78-L127)):
- its current program counter (`PC`),
- its typed register environment (`Data`),
- its lifecycle status (`Status`: `"open"`, `"succeeded"`, `"failed"`, `"abandoned"`, or `"cancelled"`), and
- its active loop-iteration cursors (`Cursors`),

alongside explicit tables for admitted observations, committed effect intents, authorization decisions, dispatch gates, external receipts, and child invocations. Because the computation is static data in a relational ledger:
1. **Any reader process** can inspect a coherent snapshot of live, interrupted, or completed work without taking ownership or registering network adapters ([`runtime.InspectExecution`](runtime/inspection.go#L11-L13), [`docs/inspection.md`](docs/inspection.md)).
2. **A fresh executor process** can open an interrupted database, fence out stale workers from the dead process, and resume from the exact committed instruction ([`runtime.Open`](runtime/runtime.go#L54-L56), [`Store.Run`](internal/executor/runner.go#L64-L66), [`Store.RunProgress`](internal/executor/runner.go#L73-L76)).
3. **A read-only verifier** can re-evaluate every historical state transition from the initial state to verify byte-for-byte internal consistency without ever touching the network ([`runtime.Replay`](internal/executor/replay.go#L23-L43)).

To understand why ALAN is structured this way—and what it refuses to oversimplify—we examine five core distinctions that ordinary agent frameworks collapse.

## 2. Five Essential Distinctions

### 2.1 Probabilistic Observations, Deterministic Residual Computation, and Authoritative World Transitions

#### Concrete Example: Document Investigation with Verified Citations
Consider ALAN's **Recoverable Document Investigator** ([`examples/investigator/README.md`](examples/investigator/README.md), [`examples/investigator/program.go`](examples/investigator/program.go)) and **Evidence Assistant** ([`examples/evidence/evidence.go`](https://github.com/JakeFAU/alan-research/blob/main/examples/evidence/evidence.go), [Monograph §5.4](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L748-L782)). Suppose the user asks: *"Is the reading room ready to reopen?"* over a snapshot of local inspection documents.

In a conventional agent loop, the language model is given a tool list and allowed to call search functions and emit a final answer directly. In ALAN, that interaction is separated into three distinct kinds of steps:

1. **The Model Output Is Recorded as an Untrusted Observation:**
   When a worker queries the OpenAI Responses adapter ([`adapters/openai/openai.go`](adapters/openai/openai.go)), the model does not execute tools or mutate program variables directly. The adapter checks HTTP and protocol completeness (for instance, rejecting responses where any root envelope, message, or reasoning item is marked `incomplete` or `in_progress`), validates the parsed fields against a closed schema ([`schema.ResultRecord`](schema/schema.go#L125-L138)), and writes a durable observation containing runtime-owned `valid` and `disposition` fields. If the model returns malformed JSON or refuses, `effects.Result` ([`effects/effects.go`](effects/effects.go#L131-L154)) normalizes all payload fields to typed zero defaults and sets `valid = false`.
2. **The Program Evaluates the Observation Deterministically:**
   Once that observation is in the worker's inbox, ALAN's pure single-step reducer ([`executor.Reduce`](internal/executor/program.go#L299-L488)) executes one instruction at a time. Before emitting a model call, pure instructions check whether `model_spent == model_limit`. After receiving a model's proposed answer and citation, pure `IfEqual` instructions compare the model's cited `document`, `version`, `snippet`, `start`, and `end` fields byte for byte against the register values returned earlier by the deterministic corpus lookup ([`adapters/lookup/lookup.go`](adapters/lookup/lookup.go)). If the model altered a single character of the quotation or fabricated a byte offset, the reducer deterministically branches to a failed or unsupported disposition without emitting an unverified answer.
3. **The Store Serializes World Commitments:**
   Computing the next state in memory still changes nothing in the database or outside world. A separate store transaction ([`Store.Commit`](internal/executor/store.go)) checks that the worker is still the active generation and epoch, marks the input observation consumed, writes the new state projection, and records any outgoing intent. Separate transactions govern whether a message is admitted to a parent's inbox or whether an HTTP worker may contact an external server.

#### Formal Foundations
In the monograph ([Monograph §1.1](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L13-L23), [§3.1–3.3](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L253-L340)), these three layers are kept disjoint:
- **Probabilistic Epistemic Proposals ($o \in \mathsf{Obs}$):** Every external input, peer message, lifecycle result, or model completion enters a run's inbox as an [`Observation`](internal/executor/program.go#L73-L80) carrying a runtime-stamped provenance tag ($\mathit{Provenance} \in \{\mathtt{"operator\text{-}input"}, \mathtt{"ordinary\text{-}message"}, \mathtt{"runtime\text{-}terminal"}, \mathtt{"runtime\text{-}lifecycle"}, \mathtt{"external\text{-}receipt"}, \mathtt{"adapter\text{-}result"}, \mathtt{"runtime\text{-}invocation\text{-}request"}, \mathtt{"runtime\text{-}invocation\text{-}outcome"}\}$). A `receive` instruction (**R-Receive** in [Monograph §3.2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L301)) requires exact 6-tuple agreement on $\mathcal{M} = \langle \mathit{kind}, \mathit{prov}, e_{\text{src}}, e_{\text{gen}}, e_{\text{obl}}, e_{\text{op}} \rangle$, preventing an ordinary message from spoofing an effect receipt ([Monograph §4.3](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L406-L425)).
- **Deterministic Residual Control ($\delta_v$):** A retained program $P_v = \langle v_{\text{sem}}, \vec{I}, \mathcal{M}_{\text{auth}} \rangle$ is a finite array over ten closed instruction forms (`set`, `add`, `branch`, `jump`, `receive`, `emit`, `end`, and the structured collection instructions `foreach`, `next`, `loop`, `append`; [Monograph §3.1.2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L271-L288)). Under operational byte limits $\mathcal{L}$ (defaulting to `1 MiB` each in [`DefaultLimits`](internal/executor/program.go#L101-L103)) and checked 64-bit integer arithmetic, the single-step reduction relation
  $$P_v, x, n, \mathcal{L} \vdash \langle \sigma, o_{\text{opt}} \rangle \xrightarrow{\;\delta_v\;} \langle \sigma', \vec{\iota} \rangle$$
  is a pure partial function (**Lemma 3.1, Strong Determinism of $\delta_v$**, [Monograph §3.2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L309-L312)). Because unrestricted backward jumps are forbidden and collection loops iterate over cloned immutable **Snapshot Cursors** $\kappa[\mathit{pc}_{\text{start}}] = \langle \mathit{Snapshot}, \mathit{Index} \rangle$ ([`internal/executor/collections.go`](internal/executor/collections.go)), every sequence of successful local reductions terminates in at most $L \cdot (M + 2)^d$ steps for code length $L$, maximum collection capacity $M$, and nesting depth $d$ (**Theorem 2.6**, [Monograph §2.5](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L226-L242)).
- **Authoritative World Transitions ($\Gamma \xrightarrow{\alpha} \Gamma'$):** The global labeled transition system ([Monograph §3.3](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L314-L340)) embeds $\delta_v$ inside explicit rules for volatile proposal creation (**G-Prepare**), pre-commit crash discard (**G-Interrupt**), fenced atomic state commit (**G-Commit**), source permission checking (**G-Authorize**), and target lifecycle mutation (**G-DecideLifecycle**).

### 2.2 Physical Recovery versus Logical Retry

#### Concrete Example: A Killed Process versus a Failed Worker
Suppose a worker agent `worker` is supervised by an inner supervisor `inner` with a retry budget of `limit = 1` ([`internal/executor/examples.go`](internal/executor/examples.go), [Monograph §2.4 Theorem 2.5](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L158-L185)). Compare two situations:

- **Case 1: The OS process crashes (`SIGKILL`) while `worker` is running.**
  `worker` (at generation `1`, commit sequence `2`, activation epoch `1`) has not failed as a program; its physical executor simply vanished. When a new process calls [`runtime.Open`](runtime/runtime.go#L54-L56) on the SQLite file, ALAN performs **physical recovery**: it validates the ledger and increments the activation epoch of every open run from `epoch = 1` to `epoch = 2`.
  - `worker` is still at **generation `1`** and **sequence `2`**, with its local registers and pending operation handles intact.
  - `inner`'s retry budget (`spent = 0`) is untouched.
  - If a zombie goroutine or stale process from `epoch = 1` somehow tries to commit a state transition late, the store rejects it with [`runtime.ErrStale`](internal/executor/store.go#L26) because its epoch (`1`) no longer matches `runs.epoch` (`2`).

- **Case 2: `worker` executes `end(outcome="failed")` on bad input.**
  Here the executor process did not crash; the program itself reached a committed terminal failure (`Status = "failed"`). Calling `runtime.Open` will *not* revive generation `1`, because generation `1` is closed. Instead, the store delivers an authenticated terminal notification for `(worker, generation=1)` to `inner`. `inner` inspects `outcome == "failed"`, checks `spent < limit`, atomically increments `spent` from `0` to `1`, and emits a `Retry` lifecycle request. When the store's `DecideLifecycle` transaction ([`internal/executor/lifecycle.go`](internal/executor/lifecycle.go#L180-L241)) accepts that request, it performs a **logical retry**:
  - Generation `1` remains permanently recorded as `"failed"` in `runs` and `history`.
  - A brand-new logical execution `(worker, generation=2)` is created at `sequence = 0, epoch = 1`, initialized from `worker`'s immutable root origin $(P_0, \sigma_0)$ in `run_origins`.
  - `inner` receives the settlement reporting `accepted = true, successor = 2`, updates its `expected` register to `2`, and sends work to generation `2`.

- **Why confusing the two is dangerous for external effects:**
  Suppose generation `1` of a subject emitted an external mutation before being abandoned, and its supervisor spawns generation `2` via `Retry`. Will an idempotent external server deduplicate generation `2`'s request against generation `1`'s request? **No.** ALAN scopes external wire keys to the logical execution `(subject, generation, sequence, ordinal)` ([`ExternalKey`](internal/executor/external.go#L93)). Because generation `1` and generation `2` have different generation numbers ($g=1 \ne g=2$), their wire keys are distinct. As demonstrated by the retained `business:order-7` witness ([Monograph §6.6 Theorem 6.7](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L937-L950)), retrying in a new generation $g+1$ without first reconciling generation $g$'s unresolved effect (or passing an application-level business key) causes even an idempotent endpoint to apply the mutation a second time. A runtime must never conflate *resuming a crashed worker for the same attempt* with *starting a new business attempt in a new generation*.

- **Why cancelling a run differs from retiring a subject:**
  Suppose supervisor $S_1$ is authorized to `Retry` worker `a` on failure (with `retry_cancelled = false`), while supervisor $S_2$ issues `CancelRun(a, generation=1)` to stop `a`. If `(a, 1)` faults just *before* `CancelRun` arrives, `(a, 1)` is already in terminal status `"failed"` (`Reason: "already_terminal"`). When $S_1$'s `Retry(a, 1)` arrives next, `(a, 1)`'s status is `"failed"`, not `"cancelled"`, so `Retry` succeeds and spawns `(a, 2)`! To permanently bar all future generations of `a`, $S_2$ must issue `RetireSubject(a)`, which sets the monotone tombstone `subjects.retired = 1` ([Monograph §7.3 Counterexample 3](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L1127-L1131), [`lifecycle.go`](internal/executor/lifecycle.go#L195-L236)).

#### Formal Foundations
ALAN stratifies identity across **four semantic tiers plus an independent authority revision** ([Monograph §4.1](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L368-L392), [`docs/foundational/02-composition.md`](https://github.com/JakeFAU/alan-research/blob/main/docs/foundational/02-composition.md#L21-L34)):

| Identity Tier | Notation | Runtime Representation | Meaning Across Failures |
| :--- | :--- | :--- | :--- |
| **1. Retained Computation** | $(P_v, \sigma)$ | [`runtime.Artifact`](internal/executor/store.go#L29-L32) + [`runtime.Projection`](internal/executor/program.go#L67-L72) | Pure serializable value; exists independently of any process or address. |
| **2. Logical Subject** | $a \in \mathsf{Subj}$ | [`runtime.Subject`](internal/executor/store.go#L33-L39) | Stable service and lifecycle target across retries until `Retired = true`. |
| **3. Logical Execution (Run)** | $x = (a, g)$ | [`runtime.RunID`](internal/executor/program.go#L36-L39) (`Generation` $g \ge 1$) | One execution generation with monotonic commit sequence $n$; survives process crashes; replaced by $g+1$ only on an accepted `Retry`. |
| **4. Physical Activation** | $(x, e)$ | `RunState.Epoch` ($e \ge 1$) under OS `flock` | Disposable OS-process lease; incremented ($e \mapsto e+1$) on `Open` without changing $g$, $n$, or $\sigma$. |
| **Authority Revision** | $w \in \mathbb{N}^+$ | `Subject.Revision` ($w \ge 1$) | Version of lifecycle ownership over $a$; orthogonal to $g$ and $e$. |

### 2.3 Intent Commitment, Authorization, Physical Application, Receipt Retention, and Settlement

#### Concrete Example: Following a Weather Lookup Across Failure Windows
Consider the **Durable Weather Agent** ([`examples/weather-agent/README.md`](examples/weather-agent/README.md), [`examples/weather-agent/program.go`](examples/weather-agent/program.go)), which calls `author.Request("op", "forecast", ...)` and then waits for the result with `author.Await("forecast", "op", ...)`.

Why does ALAN split an external call into two separate instructions (`emit` followed by `receive`) and a multi-stage durable protocol instead of a single `callAdapter()` step? Because between the moment a program decides to make a call and the moment its continuation uses the response, **four distinct crash and cancellation windows** exist ([Monograph §5.2–5.3](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L646-L738)):

1. **Proposal before Commit (Window $W_1$):**
   The reducer evaluates the `emit` instruction in volatile memory. If `SIGKILL` hits before the SQLite transaction commits, the uncommitted proposal disappears. Because physical dispatch is never triggered inside `Reduce`, no phantom HTTP request can ever be sent from an uncommitted step.
2. **Intent Commitment before Authorization and Reservation (Window $W_2$):**
   [`Store.Commit`](internal/executor/store.go) atomically persists the new program counter, any local register updates (such as incrementing a `spent` counter), and the immutable [`Intent`](internal/executor/program.go#L81-L91) record $\iota$ with operation ID `[subject, generation, sequence, ordinal]`. At this cut, the intent is `committed` ([`runtime.EffectCommitted`](runtime/inspection.go#L75)), but no permission check or budget reservation has occurred yet.
   - If a supervisor cancels or retires the run *before* its first source permission check (`AuthorizeIntent`), the permission check serializes after the cancellation and records a permanent refusal (`source_closed` or `source_retired`, [`runtime.EffectAuthorizationRefused`](runtime/inspection.go#L77)). By **Theorem 5.4 (first clause)** ([Monograph §5.3](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L728-L731)), the trusted dispatcher can never launch that mutation.
   - If the source is eligible, the runtime records source authorization, validates pure adapter preparation (`Adapter.Prepare` in [`effects/effects.go`](effects/effects.go#L102-L110), which serializes and hashes the exact wire request without I/O), checks the capability grant and root effect ceiling, and commits an attempt reservation (`adapter_attempts` / `external_attempts` and `composition_reservations`).
3. **The Local Dispatch Gate vs. Physical Application (Window $W_3$):**
   Suppose an operation has been authorized and reserved, and *then* an operator cancels the run or revokes authority just before the background HTTP worker actually calls the network. During Phase 2A, adversarial experiments showed that a worker holding an earlier reservation could still launch after source cancellation (**Withdrawn launch clause of Theorem 5.4**, [Monograph §5.3](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L732)).
   - To close this gap locally, Phase 2B introduced the **local dispatch admission gate** ([`admitDispatch`](internal/executor/runner.go#L254), [`docs/dispatch-admissions.md`](docs/dispatch-admissions.md)). Under the single-host owner lock, immediately before spawning the background transport goroutine, the store re-checks that the source generation, revision, projection, enclosing scope, and any delegated authority path are still open and valid, and (in formats 9–12) appends a durable dispatch-admission fact.
   - If revocation wins before the gate, no worker is launched; the reservation remains spent (`spent_before_dispatch` in [`docs/bounded-series.md`](docs/bounded-series.md#L101)), and the physical execution bound is provably `0`.
   - If the gate wins before revocation ($A(w) < R < L(w)$), the already admitted worker may still enter HTTP execution; after revocation, the host can call `Store.AwaitDispatchQuiescence` to wait until all covered local workers have finished handling their return or withdrawal ([Monograph §5.3 Phase 2B](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L734-L738)).
   - While the worker is in flight (or if `SIGKILL` kills the process after the gate before a result is recorded), the local effect is in state `reserved_unknown` ([`runtime.EffectReservedUnknown`](runtime/inspection.go#L80), `outcome_unknown`). Notably, background transport workers hold no store lock across network I/O (`runner.go`), so a slow HTTP request never starves ready local reductions in peer runs ([Monograph §7.4 Counterexample 4](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L1133-L1135)).
4. **Receipt Retention, Conflict Preservation, Settlement, and Consumption (Window $W_4$):**
   When the transport worker receives a response, draining and recording it uses a bounded, cancellation-independent cleanup context (`context.WithoutCancel` in [`runner.go`](internal/executor/runner.go#L124)) so a caller context timeout at the dequeue boundary cannot drop an already received response ([Monograph §7.5 Counterexample 5](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L1137-L1140)). Even here, ALAN distinguishes three final transitions:
   - **Receipt/Result Retention (`result_unsettled`):** The validated response is written to `external_receipts` or `adapter_results`. If a second, distinct valid receipt later arrives for the same original operation, the first result remains the sole winner for program settlement, while the store atomically promotes its physical format (`3/4/5` → `6/7/8`, or `9/11` → `10/12`) and records the conflicting receipt in `receipt_conflicts` (**Lemma 5.3**, [Monograph §5.3](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L722-L726), [`receipt_conflict.go`](internal/executor/receipt_conflict.go)).
   - **Settlement (`settled`):** A separate transaction writes a `settlements` row and admits the correlated result observation into the waiting run's `observations` inbox.
   - **Consumption (`selected`):** The waiting run executes its `receive` (`author.Await`) instruction in a committed `history` step, setting `consumed_sequence` (`SelectedAt` in [`docs/inspection.md`](docs/inspection.md#L48-L65)) and binding the payload into its registers.

#### Formal Foundations
In [Monograph §5.1–5.3](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L630-L726), ALAN relates its retained programs to Xia et al.'s (2020) **Interaction Trees ($\mathsf{ITree}_{E,R}$)**:
- At the pure syntax level, factoring an effect call into `emit` and `receive` is a standard free-monad lowering $\mathcal{S} : \mathsf{ITree}_{E,R} \to \mathsf{ITree}_{E_{\text{split}}, R}$ over $E_{\text{split}} = \mathsf{Emit} \uplus \mathsf{Receive}$ (**Proposition 5.1**, [Monograph §5.2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L653-L660)).
- However, standard monadic $\mathsf{ITree}$ interpretation (`interp`) evaluates each handler step synchronously inside the evaluator's thread and cannot represent Windows $W_1$–$W_4$. ALAN therefore defines the **Split-Phase Journaled Handler Algebra ($\mathcal{H}_{\text{journal}}$)** over the **Epistemic Effect Lattice ($\widehat{\mathbb{O}}_{\text{eff}}$, Definition 5.2)** ([Monograph §5.3](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L673-L720)):
  - Consistent states of a single original operation are $\bot_{\text{unauth}}$ (no decisive reservation), $\mathsf{Suppressed}(r)$ (decisive refusal with reason $r \in R$), $\mathsf{Unknown}$ (allowed reservation, remote application unresolved), and $\mathsf{Known}(v)$ (verified canonical receipt $v \in V$), ordered by $\bot_{\text{unauth}} < \mathsf{Suppressed}(r)$ and $\bot_{\text{unauth}} < \mathsf{Unknown} < \mathsf{Known}(v)$, with top element $\top_{\text{conflict}}$ joining conflicting denials or distinct receipts $K_v \sqcup K_w = \top_{\text{conflict}}$.
  - Whenever $R$ and $V$ are nonempty, $\{\bot_{\text{unauth}}, \mathsf{Unknown}, \mathsf{Known}(v), \mathsf{Suppressed}(r), \top_{\text{conflict}}\}$ forms the pentagon lattice $N_5$, which is nonmodular, nondistributive, and ungraded ([Monograph §5.3](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L720)).

### 2.4 Computation Persistence versus Knowledge of External Effects

#### Concrete Example: Matching Local Exports with Opposite World Histories
Persisting an agent's program counter and registers in SQLite means we never lose track of what the agent was doing. Does that mean a recovered process knows what happened in the outside world?

Consider the **Phase 3B.7 Matched Concrete Effect Histories** experiment ([Monograph §6.15](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L1100-L1108), [`docs/foundational/phase3b7/05-results.md`](https://github.com/JakeFAU/alan-research/blob/main/docs/foundational/phase3b7/05-results.md)). Two branches are copied from the same closed SQLite seed database (verified by matching seed file lengths and hashes). In both branches, an authorized, debited, and gate-admitted service call enters the in-flight barrier:
- In the **zero branch**, the worker is held before contacting the HTTP endpoint until `SIGKILL` terminates the owner process. The endpoint records **0 contacts and 0 applications**.
- In the **applied branch**, the worker sends the HTTP request, the endpoint commits the increment (**1 contact and 1 application**), and `SIGKILL` terminates the owner process before the HTTP response is recorded locally.

Both branches then reopen the database once (`epoch 2 → 3`), revoke the delegating authority root, and refuse a fresh dispatch gate. While the qualification checker treats the archived raw `.sqlite` database files as opaque bytes, **the complete post-open, stopped, reopened, and final local exports (`inspect.json`, covering all 41 exported SQLite tables and 94 rows) and the final `run.json` reports match byte for byte and structure for structure between the zero branch and the applied branch** ([`05-results.md`](https://github.com/JakeFAU/alan-research/blob/main/docs/foundational/phase3b7/05-results.md#L14-L35)).

This concrete witness illustrates a fundamental law of crash-consistent interactive computation: **local state exports cannot distinguish a pre-transmission crash after gate admission from a post-application crash before receipt recording.** Consequently, any recovery procedure that inspects only the local store must carefully distinguish what kind of external operation was interrupted:
- Automatically re-sending an interrupted non-idempotent request (or an ordinary adapter attempt) would apply the effect a *second* time in the applied branch.
- Inventing a synthetic failure or default observation so the waiting agent can proceed would cause the agent's continuation to execute on false premises in the applied branch.

ALAN resolves this by distinguishing four recovery and continuation mechanisms according to the operation's profile and explicit operator or ledger authority:

1. **Historical Verification (`runtime.Replay`):**
   Opens the SQLite file in read-only mode (`mode=ro`, `PRAGMA query_only = 1`), folds $\delta_v$ over every committed row in `history`, verifies byte-exact JSON equality of reconstructed projections and intents, checks foreign keys and causal ordering constraints, and rolls back on close ([`internal/executor/replay.go`](internal/executor/replay.go#L23-L43)). It holds no adapter registry or HTTP client and can never contact an external endpoint.
2. **Idempotent Raw External Attempts (`cmd/alan --profile idempotent`):**
   Each store generates a random 256-bit namespace $\mathcal{N}_{256}$ at creation ([`store.go`](internal/executor/store.go)) and stamps every outgoing raw external request with $\mathsf{ExtKey}(\mathcal{N}_{256}, (a, g), n, k)$ ([Monograph §4.3 Definition 4.2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L420-L425)). On recovery under the idempotent profile, if current dispatch admission still permits, re-presenting that same immutable wire key to a cooperating idempotent endpoint either applies the original operation for the first time (in the zero branch) or retrieves the stored receipt (in the applied branch) without a second mutation.
3. **Original Non-Idempotent Attempts and Ordinary Adapter Calls (`ConsequenceUnresolved`):**
   When an allowed non-idempotent raw request or an ordinary adapter attempt (such as an OpenAI call in [`examples/investigator`](examples/investigator/README.md#L73-L75) or an individual forecast lookup in [`examples/weather-agent`](examples/weather-agent/README.md#L45)) has passed local dispatch admission and has no recorded result after a crash, recovery **withholds automatic retransmission of that original attempt and refuses to fabricate a result**. The reservation for that attempt remains spent, its waiting run remains `"open"` at its `receive` instruction (`outcome_unknown`), independent ready runs continue to advance, and the unresolved original operation is surfaced in `RunReport.UnknownExternal` / `UnknownAdapters` and [`runtime.ConsequenceUnresolved`](runtime/inspection.go#L90).
4. **Controlled Receipt Reads (`adapters/receiptquery`) and Newly Approved Bounded Observations (`Store.ApproveContinuation`, `author.BoundedSeries`):**
   Holding an interrupted original attempt as `outcome_unknown` does *not* mean the system is permanently stuck or unable to make future observations:
   - *Newly Approved Bounded Observations (Formats 11/12):* In the weather agent ([`docs/continuations.md`](docs/continuations.md), [`docs/bounded-series.md`](docs/bounded-series.md)), a failed or unresolved Open-Meteo request on `weather-1` never permanently prevents future weather readings when allowance remains. Reopening the store preserves `weather-1` attached to its original operation ID without re-sending it, while an operator can inspect the cut via `cut.ContinuationBasis(next)` and explicitly approve the next slot `weather-2` (`weather-agent refresh --read 2`, calling `owner.ApproveContinuation(ctx, basis, reason)`). The store verifies in an atomic transaction that `weather-1`'s paid reservation and evidence match `basis`, and then `weather-agent resume` executes `weather-2` as a distinct, separately charged observation in its own resource root.
   - *Controlled Receipt Read and Adoption (Formats 5/8, Phase 2C/2D):* When an external resource maintains a queryable application ledger ([`internal/fixture/ledger.go`](internal/fixture/ledger.go), [`adapters/receiptquery`](adapters/receiptquery/protocol.go)), ALAN separates the issuing run from a separately rooted resolver run, and requires two distinct grants ([`runtime.ReceiptGrant`](runtime/runtime.go#L82)): permission to **read** the original operation's wire match on the ledger (spending one of two durable read opportunities) and permission to **import/adopt** a unique found receipt to reconstruct the missing counter result ([Monograph §5.3 Phase 2C/2D](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L740-L746), [§6.5](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L927-L935)). Even then, finding no match on the ledger only proves that no application was visible at that snapshot—an in-flight packet could still apply later.

#### Formal Foundations
In [Monograph §6.1–6.7](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L788-L963), global configurations are factored into $\Gamma = \langle \mathcal{D}, \mathcal{V}, \mathcal{W} \rangle$ (Durable Store $\mathcal{D}$, Volatile Activation $\mathcal{V}$, and External World $\mathcal{W}$):
- **Proposition 6.1 (Impossibility of Unconditional Symmetric Crash Bisimulation in Non-Idempotent Window $W_3$, [Monograph §6.3](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L853-L860)):** No deterministic recovery operator $\mathsf{Recover}(\mathcal{D})$ lacking an out-of-band read channel to $\mathcal{W}'$ can simultaneously guarantee at-most-once world safety ($\#\mathsf{Apply} \le 1$) and symmetric forward bisimulation with an uninterrupted run across a Window-$W_3$ crash.
- **Theorem 6.6 (Two-Regime Durable Computation, [Monograph §6.5](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L900-L920)):**
  - *Part I (Proved — Invariant I4):* $\mathsf{Replay}(\mathcal{D})$ terminates, reconstructs the exact committed projections $\hat{\sigma}_s = h_s.\mathit{successor}$ and intents $\hat{\vec{\iota}}_s = h_s.\mathit{intents}$ for every run, and leaves $\mathcal{D}$ and $\mathcal{W}$ byte-for-byte invariant. Moreover, every read-only snapshot $\mathcal{D}$ forms a **Chandy–Lamport Consistent Cut** with respect to the causal order $\prec_{\text{ALAN}}$ (**Proposition 6.8**, [Monograph §6.7](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L956-L963)). *(Note: Because `Replay` folds the same reducer $\delta_v$ over the compiled program $P_v$, `Replay` proves historical execution consistency, not compiler lowering correctness—see [Monograph §7.2 Counterexample 2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L1120-L1125).)*
  - *Part II & Part III (Qualified Safety vs. Open Future Simulation):* Recovery preserves the logical store cut $\pi_{\text{logical}}(\mathcal{D})$ (when $\mathsf{Unresolved}_{\text{non-idem}}(\mathcal{D}) = \emptyset$) and enforces conservative no-repeat/no-fabrication safety (when $\mathsf{Unresolved}_{\text{non-idem}}(\mathcal{D}) \ne \emptyset$). Extending those local properties to full future **Symmetric Observational Bisimulation Modulo Epoch Abstraction ($\approx_{\mathrm{obs}}$, Definition 6.3)** or **Directed Epistemic Prefix Simulation ($\preccurlyeq_{\mathrm{ep}}$, Definition 6.4)** remains an explicit open proof obligation whenever peers compete for shared resource budgets, share scope closure, or interact with uncoupled external endpoints ([Monograph §6.4–6.5](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L868-L920)).

### 2.5 Composition, Resource Conservation, Authority, Result Custody, and Progress

#### Concrete Examples Across Multi-Agent Topologies

1. **Supervision Without Privileged Runtime Classes (and Why Authority Is Orthogonal to Creation):**
   In ALAN, there is no special `Supervisor` or `Coordinator` runtime object; a supervisor is an ordinary program that receives observations and emits intents ([Monograph §2.4](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L156-L208)).
   - *Why must a parent have an explicit terminal-observation route?* Suppose a child worker computes a result silently and ends without a public terminal notification route, writing its status only to a private ledger. The **Ledger-Only Boundary Lemma** ([Monograph §2.4](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L188-L200)) proves by two-sided step induction that for *every* well-formed parent program $P$ at that boundary, the parent's finite trace set is identical whether the child succeeded ($b=0$) or failed ($b=1$): $\mathrm{Tr}_p(C_0[P]) = \mathrm{Tr}_p(C_1[P])$. Therefore, even a zero-retry supervisor cannot propagate child success/failure without an explicit channel—supplied in ALAN by the authenticated terminal observation route $T(a, p, o, w_a)$.
   - *Does being able to observe or message a child allow a parent to retry or cancel it?* **No.** By **Theorem 4.1 (Authority Non-Amplification — Invariant I3)** ([Monograph §4.2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L394-L404)), creation provenance ($\mathcal{G}_{\text{prov}}$), ordinary message permission ($M \in \mathcal{G}_{\text{comm}}$), terminal observation permission ($T \in \mathcal{G}_{\text{comm}}$), and lifecycle mutation permission ($L \in \mathcal{G}_{\text{life}}$) are checked independently in [`permissions`](internal/executor/store.go#L109). A monitor granted $T$ can receive a worker's failure observation and still be refused `Retry` with `grant_denied` if it lacks $L$. (Conversely, if a parent *is* granted $L$ on a static child but lacks $T$, issuing a post-`End` `Retry` probe reveals whether the child failed via the lifecycle settlement `accepted = true` vs. `not_retryable`—showing that independent grants do not imply observational noninterference when lifecycle settlements are visible; [Monograph §2.4](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L205) & [§4.2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L404).)

2. **Bounded Template Invocations, Root Resource Conservation, and Non-Starvation:**
   When a parent invokes multi-agent sub-networks—such as the two workers in [`examples/investigator`](examples/investigator/program.go) (`author.Invoke` / `author.AwaitInvocation`) or an ordered collection of up to $M$ work items in [`compose.New`](compose/collection.go#L25-L104)—how does ALAN prevent resource amplification and thread-pool deadlocks?
   - **Why resource accounting must be rooted at the public boundary:** In Phase 1B, an adversarial review constructed a 37-event nested composite where a provider accepted *one* public request $r_{\text{root}}$ and emitted *two* internal sub-requests $r_{\text{sub},1} \ne r_{\text{sub},2}$ to a worker, mutating an external resource twice while hiding the internal channel ([Monograph §3.4](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L354-L356)). To prevent nested components from amplifying work behind hidden channels, ALAN attaches an immutable **Root Resource Envelope** $\mathcal{B}(r) = \langle D_{\max}, I_{\max}, R_{\max}, E_{\max}, C_{\text{phys}} \rangle$ ([`runtime.ResourceLimits`](runtime/runtime.go#L65-L66)) to each composition root $r$, bounding nesting depth $D_{\max}$ (default `3`), total admitted invocations $I_{\max}$ (default `32`), total created runs $R_{\max}$ (default `64`), total effect reservations $E_{\max}$ (default `96`), and concurrent physical transport workers $C_{\text{phys}}$ (default `1` or `2`).
   - **Strict Conservation & Waiting-Parent Slot Freedom (Theorem 4.4, [Monograph §4.4](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L441-L451)):** Every `AdmitInvocation` ([`internal/executor/invocation.go`](internal/executor/invocation.go#L220-L534)) atomically checks the accumulated charges in `composition_charges` before creating member runs, and crash recovery never resets those charges. Furthermore, because a parent suspended at `AwaitInvocation` (`receive(kind="invocation")`) is merely an open projection row in SQLite and holds **zero** Go goroutines or HTTP worker slots in $C_{\text{phys}}$, leaf workers at depth `3` can acquire the sole physical transport slot even when $C_{\text{phys}} = 1$ without deadlocking behind their waiting ancestors.
   - **Why substituting components inside a shared budget is subtle:** Suppose a direct leaf program `A` computes locally while a replacement `B` invokes an internal helper (spending one extra invocation and created run). In **owning trees** built from callable joins (`J`), diagnostic relays (`Relay`), and binary forks (`Fork`) (**Phases 1L–1T**, [Monograph §4.5.2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L567-L627)), where each parent owns its children and awaits them by their opaque original operation handles (**Phase 1R** nominal permutation check), substituting `B` for `A` preserves every returned answer and failure diagnosis (`candidate_failed` vs. `candidate_missing_reply`) under an open scope and a common sufficient allowance. However, when a parallel peer shares the same tight root budget or scope:
     - An intervening peer singleton debit at remaining allowance $(I, R) = (1, 1)$ can shift a candidate's refusal reason from `created_run_limit` to `invocation_limit` (**Peer Refusal Witness**, [Monograph §4.5.2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L524-L541)).
     - A root caller that succeeds before a parallel peer starts closes the composition scope (`scope_closed` in [`compositionScopeClosed`](internal/executor/invocation.go#L165-L216), **Phase 1I negative result**, [Monograph §4.5.2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L545)).
     - An ordinary peer that terminates after committing a report message but before that message's first source authorization gets refused with `source_closed` (**Phase 1J/1K**, [Monograph §4.5.2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L551-L560)), whereas an invoked entry-member's bound reply receives an explicit protocol exemption so its diagnostic can still reach its owning parent (**Phase 1N**, [Monograph §4.5.2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L587)).

3. **Result Custody vs. Progress vs. Authority in Two-Agent Delegation (Phases 3A & 3B.1–3B.5):**
   Even when two agents each have durable local storage, combining them exposes three distinct boundaries:
   - **Result Custody vs. Delivery Acknowledgment (Phase 3A, [Monograph §6.8](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L967-L979)):** Suppose agent $A$ delegates a request to agent $B$, $B$ computes result $r$ and sends it to $A$, $A$ receives $r$ in volatile memory and immediately sends a delivery ACK, $B$ deletes its retained copy of $r$ upon receiving the ACK, and then $A$ crashes before writing $r$ to disk. Both agents obeyed their local durability rules, yet the result $r$ is permanently lost! Continuous **result custody** ($D_B = r \lor D_A = r$ at every reachable state after application) holds if and only if $B$ releases its copy only upon an authentic ACK caused *after* $A$ has durably recorded $r$ (an explicit instance of Saltzer, Reed, and Clark's 1984 end-to-end argument; in ALAN's `Store`, accepted observations are written to SQLite inside the admission transaction before any acknowledgment is recorded).
   - **Result Custody vs. Progress in Reciprocal Obligations (Phase 3B.1, [Monograph §6.9](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L983-L1001)):** Suppose $A$ and $B$ each commit a request to the other, and both agents are *serial*—each restricts **incoming request application** while its own outgoing request is committed and unconsumed ($\mathsf{Trap} = c_{AB} \land c_{BA} \land \neg a_{AB} \land \neg a_{BA}$). Importantly, the serial policy restricts only incoming *application*; it does **not** restrict request admission into the inbox, receipt transmission/recording/consumption, or acknowledgment handling. In fact, in the single-Store public-runtime fixture, both requests are admitted and delivery-acknowledged before `Run`, result custody is never violated, and the Store reports `Quiescent = true` with zero pending transport deliveries and zero `UnresolvedIntents`—yet two admitted requests remain unconsumed and neither agent can ever complete its work! Progress requires that at least one agent be *servicing* (permitting incoming request application while waiting on its own outgoing request).
   - **Reciprocal Service vs. Request-Bound Authority and Revocation (Phases 3B.2–3B.5, [Monograph §6.10–6.13](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L1003-L1086), [`examples/delegation`](examples/delegation/README.md)):** Even when $A$ is willing to serve $B$ while waiting, $A$ may not hold the permission $b = (\mathsf{increment}, \mathsf{counterB}, \mathsf{blue})$ required to execute $B$'s request. If $A$ borrows $B$'s permissions implicitly without consent (`S3`), or combines $A$'s resource with $B$'s scope (`Cartesian mutant`), it violates authority safety. Instead, ALAN implements opt-in **request-bound one-hop delegation and revocation** (`DelegateAuthority` and `RevokeAuthority` in formats 13–16; [`internal/executor/request_authority.go`](internal/executor/request_authority.go), [`internal/executor/request_binding.go`](internal/executor/request_binding.go)):
     - In `alan/request-authority/v1` (formats 13/14, [`examples/delegation/reciprocal.go`](examples/delegation/reciprocal.go)), $A$'s delegated service emission had to *immediately* follow the reduction that selected $B$'s request; if $A$ selected a `ready` message in between, the runtime refused with `authority_request_not_admitted` ([Monograph §6.11](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L1039)).
     - In `alan/request-authority/v2` (formats 15/16, [`examples/delegation/request_binding.go`](examples/delegation/request_binding.go), [`docs/qualification/phase3b4/README.md`](docs/qualification/phase3b4/README.md)), the grant binds the exact original request $q$ to the exact service operation $e$, verifying via existing `observations` and `history` rows that $A$ genuinely selected $q$ at an earlier sequence ($0 < c_{\text{seq}} < e_{\text{seq}}$) in the same generation—allowing finite intervening scratch steps and `ready` selections without introducing any new binding table.
     - Crucially, **first authorization** is immutable, whereas **every fresh physical admission gate** re-checks whether the selected authority root has been revoked (`RevokeAuthority`). In the two-root model `S2/SeparateGrantRevocation` (**Phase 3B.5**, [Monograph §6.13](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L1069-L1086)), revoking $B$'s root $b$ blocks fresh admissions through $b$, while a BA opportunity admitted *before* revocation can still complete in its surviving server activation and unlock $B$'s serial gate to finish AB under $B$'s distinct root $c$.

#### Formal Foundations
In [Monograph §4.5](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L453-L521), ALAN formulates **Budget-Indexed, Interface-Scoped Failure/Divergence Bisimulation ($\approx^{\Delta}_{I,\mathcal{B}}$, Definition 4.6)** over admissible contexts $C[\cdot] \in \mathcal{C}_{\text{adm}}$ (**Definition 4.5**). Because message admission into a run's inbox is asynchronous while `receive` consumption is synchronous, $\approx^{\Delta}_{I,\mathcal{B}}$ tracks a **Dual Public Readiness Pair**:
1. **Mailbox Admission Readiness** $\mathsf{AdmReady}_I(\Gamma)$ (which target subjects are open, unretired, and permitted to accept a message into their inbox), and
2. **Continuation Consumption Readiness** $\mathsf{WaitReady}_I(\Gamma)$ (which 6-tuple correlation guards $\mathcal{M}$ an open run is currently suspended at).

### 3.2 Authoring Surface vs. Raw Executor Surface and Storage Formats

1. **Authoring vs. Raw Instructions:**
   The public `author` compiler exposes structured steps (`Set`, `Add`, `IfEqual`, `Repeat`, `ForEach`, `Append`, `Send`, `Receive`, `Request`, `Await`, `Invoke`, `AwaitInvocation`, `Success`, `Failure`). By design, `author` does *not* expose raw numeric program counters, backward `Goto`, raw `runtime-terminal` waits, or raw lifecycle `emit` instructions (`Retry`, `CancelRun`, `AbandonRun`, `RetireSubject`, `DelegateAuthority`, `RevokeAuthority`). Those lower-level capabilities are implemented in the underlying `alan/1d/v1` instruction calculus (`internal/executor`) and can be provisioned as raw `runtime.Artifact` programs (as in [`cmd/alan`](cmd/alan/main.go), [`examples/delegation`](examples/delegation/request_binding.go), and the Phase 1K raw terminal receiver; see [Monograph §2.4](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L186) & [§4.5.2](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L564-L565)). Moreover, on the invocation profile, `DecideLifecycle("Retry")` currently refuses invoked template members with `invocation_retry_unsupported` ([Monograph §6.4 Definition 6.5](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md#L890)).
2. **Physical SQLite Storage Formats (3 through 16):**
   Rather than forcing migrations or adding tables to deployments that do not use optional protocols, ALAN versions its physical store formats explicitly ([`docs/inspection.md`](docs/inspection.md#L88-L97), [`examples/delegation/README.md`](examples/delegation/README.md#L18)):
   - **Formats 3 / 6:** Ordinary provisioned runs, retry origins, messages, lifecycle decisions, and external/adapter effects (`6` after retaining conflicting receipt evidence in `receipt_conflicts`).
   - **Formats 4 / 7:** Complete finite composition (`composition_*` tables, root envelopes, template invocations, and outcome publications; `7` with conflicting receipts).
   - **Formats 5 / 8:** Composition plus the controlled receipt-read and adoption protocol (`8` with conflicting receipts).
   - **Formats 9 / 10:** Composition with opt-in local dispatch-admission journaling (`RecordDispatchAdmissions: true`; `10` with conflicting receipts; [`docs/dispatch-admissions.md`](docs/dispatch-admissions.md)).
   - **Formats 11 / 12:** Composition with protected operator continuation slots (`ContinuationSlot`, used by `author.BoundedSeries` and `examples/weather-agent`; `12` with conflicting receipts; [`docs/continuations.md`](docs/continuations.md)).
   - **Formats 13 / 14:** Opt-in request-bound authority delegation `alan/request-authority/v1` with immediate-predecessor selection (`14` with conflicting receipts; [`docs/qualification/phase3b3/README.md`](docs/qualification/phase3b3/README.md)).
   - **Formats 15 / 16:** Opt-in request-bound authority delegation `alan/request-authority/v2` with historical per-generation selection binding across finite intervening steps (`16` with conflicting receipts; [`docs/qualification/phase3b4/README.md`](docs/qualification/phase3b4/README.md)).
3. **Explicit Unimplemented Scope:**
   As stated in [`README.md`](README.md#L96), multi-host distributed ownership, general dynamic spawning outside retained template catalogues, PostgreSQL storage, history compaction, automatic schema migration, and a managed tool/provider control plane are intentionally unimplemented.

## 4. Epistemic Guide: What Is Proved, Conditional, Model-Checked, Witnessed, and Open

A central rule of the ALAN project ([`AGENTS.md` §2 & §8](https://github.com/JakeFAU/alan-research/blob/main/AGENTS.md)) is never to conflate a mathematical proof with a conditional argument, a finite-state model check, a concrete runtime test, or an open conjecture. The table below maps the exact status of ALAN's foundational claims and provides direct entry points into the monograph ([`paper/alan-dissertation.md`](https://github.com/JakeFAU/alan-research/blob/main/paper/alan-dissertation.md)):

| Category | Claim / Mechanism | Exact Scope & Assumptions | Monograph & Repository Links |
| :--- | :--- | :--- | :--- |
